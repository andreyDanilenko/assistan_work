# Как читать код и понимать работу приложения

Начните с пути `watch`: это основной рабочий режим. Остальные команды — отдельные инструменты для проверки доступа, запроса логов и анализа файла. Их не нужно читать, чтобы понять мониторинг.

**Приложение — один процесс `lokictl`.** CLI выбирает режим при запуске. В режиме `watch` внутри процесса работают сбор логов и приём команд Telegram. Сам Telegram-клиент ничего не запускает: он выполняет запрос, когда его метод вызывает другой компонент.

## 1. Общая картина

```text
Терминал: lokictl watch
  → cli.Parse: разобрать команду и флаги
  → main.run: прочитать конфиг, выбрать сценарий
  → main.runMonitor: создать и соединить компоненты
  → monitor.RunWithCommands
      │
      ├─ Цикл мониторинга
      │    Loki → SQLite → анализ сохранённого периода
      │         → краткая сводка → очередь → Telegram
      │
      └─ Приём команд Telegram (параллельно)
           /report или кнопка → SQLite → анализ периода
                             → подробный TXT → Telegram
```

**CLI не является посредником между Telegram и монитором.** `cli.Parse` выполняется один раз при запуске. В обычном `watch` функции `cli.Run` и сервис `app.Service` не вызываются. `/report` обрабатывает пакет `telegram`, повторного запуска CLI и запроса в Loki нет. Сообщения о ходе мониторинга в терминале печатает сам `monitor`.

Не обязательно читать файлы целиком. Найдите указанные функции и следуйте вызовам.

## 3. Что делает один цикл `watch`

При обычных настройках используется `WATCH_REPORT_ONLY=true`.

1. Удаляет из SQLite записи старше 48 часов. Очистка выполняется и при недоступном Loki.
2. Вычисляет свежее окно: конец — сейчас минус 10 секунд; начало — за 2 минуты до конца, но не раньше запуска процесса.
3. Получает окно через `loki.FetchLogs`. Если данных много, читает его частями в пределах установленного бюджета. Полностью полученные части сохраняет вместе с отметкой покрытия.
4. Проверяет состояние источника и отсутствие логов. Для вывода «логов нет» нужны подтверждённые данные, а не просто неудачный запрос.
5. Когда наступает срок сводки, читает накопленный период из SQLite, считает заказы и ошибки, оформляет сообщение и ставит его в очередь.
6. Сохраняет состояние уведомлений и пытается отправить очередь в Telegram.
7. Ждёт до следующего цикла. Обычно пауза после работы — 2 минуты; она может сократиться до ближайшего срока сводки.

Сводка отправляется примерно раз в 15 минут. Её фактические границы указаны в сообщении; первый период текущего запуска может быть короче. Сбор и отправка имеют разные интервалы.

**Догрузки прошлых пропусков и автоматического повтора неудачного запроса Loki сейчас нет.** Новый цикл выбирает свежее окно. Чтение нескольких страниц текущего окна — часть текущего сбора. Первый цикл после запуска ждёт из-за задержки конца окна на 10 секунд.

Время обработки, сон компьютера и запоздавшие события могут оставлять пропуски. Покрытие в отчёте показывает подтверждённые участки; этот режим предназначен для наблюдения за тенденцией. `--timeout` ограничивает отдельные этапы, а не суммарное время всего цикла.

## 4. Как работает Telegram

Здесь два независимых действия: отправка автоматических сводок и обработка запросов человека.

### Автоматическая сводка

```text
monitor.queuePeriodicReport
  → переданный BuildSnapshot → main.databaseSnapshot
      → storage.ReadRange: записи и покрытие периода
      → monitor.Analyze: заказы и ошибки
      → storage.LookupResellers + monitor.EnrichResellers: дополнить реселлеров
  → monitor.summaryText: короткий текст
  → очередь в состоянии монитора
  → monitor.deliver
  → telegram.Client.SendMessageWithReport: сообщение с кнопками
```

История из базы помогает найти реселлера, если его ID отсутствует в выбранном периоде. Она не добавляет прошлые ошибки в счётчики этого периода. Названия реселлеров берутся из справочника, загруженного при запуске.

### Команда `/report 16h` или кнопка

```text
telegram.RunReports: получить обновления от Telegram
  → проверить чат, команду/кнопку и период
  → переданная функция buildReport (создана в main.runMonitor)
      → main.databaseSnapshot: прочитать базу и посчитать результат
      → report.WriteDatabase: оформить подробный TXT
  → telegram.Client.SendDocument: отправить файл в чат
```

- [telegram/reports.go](internal/telegram/reports.go) отвечает за команды, кнопки, ограничения запросов и период отчёта.
- [telegram/client.go](internal/telegram/client.go) отвечает за HTTP-вызовы Telegram: получить обновления, отправить текст или файл, подтвердить кнопку.
- [report/text.go](internal/report/text.go) оформляет TXT: итоги, категории ошибок, реселлеры и списки ID заказов. Файл содержит посчитанный результат, а не новую выгрузку сырых логов.

Приём команд работает параллельно со сбором: обычно проверяет обновления с паузой 2 секунды, после ошибки ждёт дольше. Сам обработчик последовательно выполняет запросы к отчётам. Он принимает их только из настроенного чата, с общим ограничением один запрос в минуту.

`/report` без аргумента означает последний час. Допустимы периоды от `1m` до `48h`, например `16h` или `20h`. Конец такого отчёта — время обработки команды. У кнопки конец закреплён за исходной сводкой: нажатие позже не сдвигает период.

Повтор доставки **автоматических сообщений Telegram** есть: неотправленное сообщение остаётся в очереди. Это не повтор получения логов. Ручной TXT после ошибки отправки автоматически не повторяется — команду нужно запросить снова.

### Что не запускает обработчик команд

`telegram-check` выполняет `checkTelegram → GetMe` и завершается. `telegram-chats` ищет ID чатов и завершается. Они не запускают бота для постоянной работы и не отправляют сводку.

`watch --once` выполняет один цикл и завершается; приём команд не запускается. `watch --dry-run` показывает предпросмотр в терминале, не открывает SQLite, не отправляет сообщения и не принимает команды. Для `/report` должен работать обычный `watch`.

## 5. Конфиг и DI простыми словами

DI здесь — передача готовых компонентов через аргументы и поля структуры. Контейнера зависимостей и скрытого поиска сервисов нет.

`main.go` соединяет компоненты. `config.Load` один раз загружает настройки: переменные окружения имеют приоритет над `.env`, затем используются значения по умолчанию. Остальные компоненты получают нужные значения явно.

| Что передаёт `main` | Кто получает | Зачем |
| --- | --- | --- |
| `*loki.Client` как `monitor.Source` | Монитор | Вызвать `FetchLogs`, не знать деталей HTTP и авторизации |
| `*storage.Store` как `monitor.Archive` | Монитор | Сохранить часть периода, проверить покрытие, удалить старые записи |
| `*telegram.Client` как `monitor.Sender` | Монитор | Отправить сообщение, не хранить токен внутри логики анализа |
| `cfg.BuildSnapshot` | Монитор | Получить посчитанный результат за период из SQLite |
| `cfg.ReadWindow` | Режим немедленных уведомлений | Прочитать записи окна для `WATCH_REPORT_ONLY=false` |
| `buildReport` | `telegram.RunReports` | Получить готовый TXT, не знать устройство SQLite и правила подсчёта |

Интерфейс описывает только нужные вызывающему методы. Например, монитору достаточно `FetchLogs`; откуда клиент берёт токен, решается при его создании. Это позволяет тестам передавать короткие подставные компоненты вместо настоящих сервисов.

`model` содержит общие данные, например `LogRecord`. Файлы `models.go` внутри пакетов содержат их собственные настройки, результаты и контракты. Это структуры и интерфейсы, а не ещё один этап выполнения.

## 6. Карта остальных файлов

| Файлы | Назначение и когда читать |
| --- | --- |
| `internal/loki/client.go`, `logs.go`, `models.go` | Авторизация и HTTP, получение/разбиение диапазона логов, настройки клиента. Читать при изменении запросов к Loki |
| `internal/storage/sqlite.go`, `models.go` | Открытие SQLite, схема, чтение записей, очистка и структуры запросов |
| `internal/storage/coverage.go` | Атомарная запись полученного диапазона и учёт покрытия. Сохранённая позиция и `Resume` остались для совместимости; нынешний `watch` их для выбора окна не вызывает |
| `internal/storage/transaction.go` | Завершение или откат транзакции на том же соединении; защита от частичной записи |
| `internal/storage/order_context.go` | Поиск реселлера по истории заказа в сохранённых данных |
| `internal/monitor/state.go` | Файл состояния, очередь уведомлений, безопасная запись и блокировка второго процесса на том же файле |
| `internal/config/resellers.go`, `examples/data.json` | Загрузка соответствия ID → название реселлера |
| `internal/model/loki.go`, `order.go`, `telegram.go`, `collection.go` | Общие модели логов, анализа файла, Telegram и покрытия |
| `internal/utils/http.go` | Общие настройки HTTP: тайм-ауты, TLS, запрет перенаправлений |
| `tests/` | Проверки компонентов и их взаимодействия; в обычном приложении не выполняются |
| `scripts/build-release.sh`, `BUILD.md` | Сборка и запуск; не участвуют в работе уже запущенного процесса |

У приложения разные файлы данных:

- `local/loki.db` — SQLite с исходными событиями и покрытием. ID заказов, типы операций и ошибки извлекаются при анализе; отдельных индексированных колонок для них пока нет.
- `local/watch-state.json` — расписание, очередь и состояние уведомлений; это не архив логов.
- Файл с суффиксом `.commands.json` — позиция обработанных команд Telegram, время последнего запроса и привязка к боту/чату. Имена привязаны к настроенному файлу состояния.

База хранит до 48 часов событий и очищается в каждом цикле работающего `watch`. Ограничение размера 2 ГБ пока не реализовано. При остановленном приложении сбор и очистка не выполняются.

## 7. Какие части используются в других режимах

| Режим | Основной путь | Что не участвует |
| --- | --- | --- |
| `watch` | `main → monitor → Loki / SQLite / Telegram` | `app.Service`, `cli.Run`, анализатор файла |
| `/report`, кнопка при работающем `watch` | `telegram → buildReport → SQLite → monitor.Analyze → report.WriteDatabase` | CLI-команды, Loki, анализатор файла |
| `logs`, `query`, `check`, метки/проекты | `cli.Run → app.Service → loki.Client → cli/output.go` | Мониторинг, SQLite, Telegram, анализ заказов |
| `analyze --file ...` | `cli.RunAnalysis → app.AnalysisService → input + analyzer → report.WriteFile` | `.env`, Loki, SQLite, Telegram, цикл мониторинга |
| `telegram-check`, `telegram-chats` | `main → telegram.Client → вывод CLI` | Loki, SQLite, цикл мониторинга |
| `db-status`, `db-cleanup` | `main.runDatabase → storage` | Loki, Telegram, анализ заказов; обе команды очищают старые записи |

**Почему два анализатора:** `internal/analyzer/analyzer.go` разбирает учебную или экспортированную историю файла для команды `analyze`. Рабочие сводки и TXT из базы считает `internal/monitor/analyze.go`. Сейчас это разные сценарии и правила, поэтому менять поведение Telegram нужно в `monitor/analyze.go`.

Для чтения офлайн-сценария порядок такой: `cli.RunAnalysis → app.AnalysisService → input/file.go → analyzer/analyzer.go → report.WriteFile`. Пакет `app` здесь координирует работу; он не является обязательным слоем каждого режима приложения.

## 8. Где менять конкретное поведение

| Хочу изменить | Начать здесь |
| --- | --- |
| Шапку и категории короткой сводки в чате | `monitor/monitor.go`: `summaryText`, `writeOrderCounts`, `writeErrorCategories` |
| Структуру скачиваемого TXT | `report/text.go`: `WriteDatabase` |
| Что считать ошибкой, успехом, типом операции | `monitor/analyze.go`; проверки в `tests/monitor/` |
| Команду Telegram или период по кнопке | `telegram/reports.go`; кнопки отправляемого сообщения — `telegram/client.go` |
| Интервал сбора или отчёта для своего запуска | `.env`: `WATCH_INTERVAL`, `WATCH_REPORT_INTERVAL`; пересборка не нужна |
| Новую настройку приложения | `config/config.go` → передача в `main.go` → конфиг нужного компонента; описание в `.env.example` |
| Состав запроса или разбор ответа Loki | `loki/logs.go`, общие данные в `model/loki.go` |
| Схему и запросы SQLite | `storage/`; не в обработчике Telegram |

## 9. Что показала проверка простоты

Слои подключаются явно, но раньше названия и порядок чтения README смешивали разные сценарии. Уточнены названия: `checkTelegram` проверяет токен, `queuePeriodicReport` готовит периодическую сводку, `processAlertWindow` обслуживает необязательные немедленные уведомления. Убрана промежуточная функция, которая только пересылала вызов оформления отчёта файла.

Самые насыщенные места — `main.runMonitor` и `monitor/monitor.go`: первое соединяет зависимости, второе содержит цикл, очередь и короткие сообщения. Для понимания их следует читать по функциям из раздела 2. Дополнительные слои и каталоги для этой проверки не вводились.

Проверки ответов, тайм-ауты, откат транзакций, ограничения отчётов и проверка чата решают конкретные задачи надёжности. Они остаются рядом с соответствующей операцией. REST, сокеты, LLM и Kafka сейчас в рабочем пути отсутствуют; документы в `spec/` содержат в том числе будущие предложения, а этот гайд описывает текущий код.
