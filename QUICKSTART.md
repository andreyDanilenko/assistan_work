# Запуск монитора на своем компьютере

Распакуйте сборку для своей ОС и процессора в отдельную личную папку. Go и SQLite устанавливать не нужно: база встроена в приложение. Откройте терминал **в этой папке**: рядом должны быть `lokictl` (Windows: `lokictl.exe`), `.env.example` и `examples/`. На Windows используйте PowerShell; во всех командах ниже заменяйте `./lokictl` на `.\lokictl.exe`.

Если запускаете из проекта `/Users/andrei/Documents/personal/loki`, выполняйте команды из его корня и заменяйте `./lokictl` на `./bin/lokictl` или `go run ./cmd/lokictl`. Остальные аргументы те же.

## 1. Подготовить доступ

На macOS/Linux:

```sh
chmod u+x ./lokictl
cp .env.example .env
chmod 600 .env
```

На Windows: `Copy-Item .env.example .env`. Копируйте шаблон только при первом запуске, не поверх существующих настроек. Редактируйте `.env` как UTF-8; имя должно быть именно `.env`, без `.txt`.

Заполните `GRAFANA_TOKEN` отдельно выданным вам токеном чтения Grafana. Адрес и проект `sds-orders` уже указаны. Для отправки нужны полный `TELEGRAM_BOT_TOKEN` — цифры, двоеточие и секретная часть — и `TELEGRAM_CHAT_ID`. Не передавайте свой `.env` другим людям. Для корпоративной Grafana может требоваться VPN и доверенный системный сертификат.

Программа сама читает `.env` из текущей папки. `source` не нужен; переменные окружения, включая пустые, имеют приоритет над файлом.

## 2. Подключить уже добавленного в группу бота

Убедитесь, что боту `@personal_assistans_botgo_bot` разрешено отправлять сообщения в эту группу.

В Telegram отправьте **именно в группе**:

```text
/start@personal_assistans_botgo_bot
```

На `/start` текущая версия не отвечает. Эта команда нужна, чтобы группа появилась в списке доступных чатов. Если используете другого бота, подставьте его username.

Затем выполните в терминале:

```sh
./lokictl telegram-check
./lokictl telegram-chats
```

В первом ответе проверьте имя бота. Во втором найдите строку с названием вашей группы и типом `group` или `supergroup`. Возьмите **chat_id**, а не ID самого бота или `user_id`.

В существующем `.env` измените `TELEGRAM_CHAT_ID`. Пример ниже вымышленный — подставьте свое значение целиком, со знаком минус:

```dotenv
TELEGRAM_CHAT_ID=-1001234567890
```

`TELEGRAM_BOT_TOKEN` остается прежним. Если монитор раньше отправлял сообщения в личный или другой чат, остановите его через **Ctrl+C** и выберите для новой группы отдельный файл состояния:

```dotenv
WATCH_STATE_FILE=local/watch-group-state.json
```

Старый файл состояния и базу оставьте на месте. После смены `.env` монитор нужно перезапустить. Дальше выполните шаги 3 и 4 ниже: предпросмотр, затем обычный `watch`.

Если группы нет в списке, проверьте имя добавленного бота, отправьте команду в группе еще раз и повторите `telegram-chats`. При сообщении об активном webhook или конфликте получения обновлений сначала остановите конкурирующий обработчик либо согласуйте подключение с его владельцем; приложение само webhook не отключает.

## 3. Проверить без отправки

```sh
./lokictl analyze --file examples/orders-analysis.txt
./lokictl check
./lokictl watch --once --dry-run
```

Первая команда разбирает учебный файл без сети. Последняя читает **реальные логи Loki** за `WATCH_WINDOW`, показывает будущие сообщения в терминале, ничего не отправляет и не меняет базу или состояние. Для нее нужны доступ к Grafana и его токен; токен Telegram и ID чата необязательны. Этот предпросмотр может читать историю до своего запуска; обычный `watch` начинает сбор с момента запуска.

## 4. Включить монитор

```sh
./lokictl watch
```

После запуска сообщения отправляются в настроенный чат, а исходные события сохраняются в `local/loki.db`. Для проверки прошлого окна без записи и отправки используйте `./lokictl watch --once --dry-run`. Обычный `--once` может завершиться на начальном ожидании новых событий. Остановка — `Ctrl+C`.

Обычный `watch` каждый цикл читает свежее окно: при стандартных настройках последние 2 минуты, но не раньше момента текущего запуска (`SessionStart`). Конец запроса отстаёт от текущего времени на 10 секунд, поэтому первый цикл ждёт, а первый сбор происходит примерно через 2 минуты. На новом файле состояния после этого сбора бот отправляет первую сводку за короткий период текущего запуска. После каждого цикла сбора выдерживается пауза 2 минуты; сводка приходит раз в 15 минут. Если отправка не удалась, причина появляется в терминале. `WATCH_REPORT_ONLY=true` отключает промежуточные сообщения о новых ошибках. При существующем состоянии расписание сохраняется, но новая автосводка не включает время до текущего запуска; первая сводка может быть короче 15 минут.

В группе бот публикует счётчики категорий ошибок с кнопкой подробностей и отвечает на `/report` структурированным TXT из локальной базы. Команды `/order` и `/status` пока не реализованы. Монитор и команды работают, пока приложение запущено на компьютере и у него есть сеть.

### Названия реселлеров

`watch` при запуске читает `examples/data.json` — JSON вида `{"ID": "Название"}`. В уведомлениях об ошибках и TXT-отчёте показывает **название и исходный ID**; одинаковые названия не объединяют разных реселлеров. Если ID отсутствует в справочнике, остаётся ID из логов. Нет файла — приложение работает без названий; ошибочный JSON нужно исправить.

Другой путь задаётся в `RESELLER_MAP_FILE` в `.env`, пустое значение отключает справочник. Путь считается от текущей папки. После правки JSON перезапустите `watch`; пересобирать бинарник не нужно. Сборка для коллег включает `examples/data.json`, если этот файл есть в проекте.

### Подробный отчёт в Telegram

Под новыми сводками есть кнопки **«📄 За этот период»**, **«📄 За 1 час»**, **«📄 За 2 часа»**. Нажмите нужную — бот пришлёт TXT с итогами по категориям и реселлерам, затем полным списком ID заказов. Все три периода заканчиваются временем исходного сообщения; время нажатия не сдвигает окно. Часовой и двухчасовой отчёты заново считают уникальные заказы по данным периода, а не складывают итоги коротких сводок. В старых уже отправленных сообщениях кнопка сама не появится.

Отчёт пересчитывается по сохранённым данным на момент нажатия: поздно поступившие логи могут уточнить числа при тех же границах периода. При смене источника или проекта старая кнопка не работает; период старше хранения 48 часов также недоступен. Для самой свежей выборки используйте `/report`:

После обновления остановите старый `watch` через `Ctrl+C` и снова запустите `./lokictl watch`. В группе отправьте:

```text
/report@personal_assistans_botgo_bot
/report@personal_assistans_botgo_bot 1h
/report@personal_assistans_botgo_bot 2h
```

Первая команда строит отчёт за последний час. Можно писать `/report` без имени бота, если Telegram доставляет такую команду этому боту. Период — от `1m` до `48h`. Ответ — один TXT с уже посчитанной сводкой проблем. Шапка содержит все уникальные заказы за период, успешные, с актуальной ошибкой, с неизвестным результатом и разбивку `new / renew / cancel`.

Далее — **итоги по категориям ошибок** и **сводка по реселлерам: название, ID, число уникальных заказов с ошибками, new / renew / cancel**. Список заказов в этой сводке не выводится. Ниже, в отдельном разделе подробностей: **вид ошибки → реселлер (название и ID) → тип → полный список ID заказов**. У заказа указаны время последней ошибки и pod/сервер, если они известны. Ограничения первыми 5 или 10 заказами нет; история событий не выводится.

Одинаковые строки ошибки не увеличивают число заказов. Заказ с двумя разными актуальными ошибками присутствует в двух разделах, но в шапке считается один раз. Последующее `order provisioned` снимает предшествующую ошибку; «ещё обрабатывается» не входит в список проблем. Ошибки без ID заказа вынесены отдельно и считаются в записях. Если актуальных ошибок нет, отчёт сообщает об этом.

ID реселлера дополняется из сохранённой истории того же заказа, проекта и источника за 48 часов до конца отчёта. Название из `examples/data.json` показывается рядом с ID; отсутствие названия не скрывает ID. Старые события нужны только для этой связи и не меняют счётчики периода. Если ID противоречат друг другу, отчёт явно показывает конфликт.

Отчёт читает записи и покрытие периода из одного снимка SQLite выбранного проекта и источника, включая сохранённые данные прошлых запусков. Он не обращается к Loki и не очищает базу. Неподтверждённые участки, в том числе промежутки между запусками, явно перечисляются; полнота относится к данным, доступным в Loki на момент сбора. Отчёт учитывает все распознанные актуальные ошибки периода: фильтры и паузы уведомлений не скрывают заказы из него. Нулевые счётчики при неполном покрытии не означают, что событий не было.

Доступ разрешён только чату `TELEGRAM_CHAT_ID`; любой участник этого чата может запросить отчёт. Не чаще одного запроса в минуту на чат. Позиция команд хранится в `WATCH_STATE_FILE.commands.json`, чтобы перезапуск не повторял рассылку. Текстовые команды старше пяти минут игнорируются; кнопки используют срок хранения своего периода. При частых нажатиях кнопка сообщает о минутной паузе. При сбое отправки автоматического повтора нет: запросите отчёт ещё раз через минуту.

Команды принимаются только обычным `watch`; `--once` и `--dry-run` их не читают. Пока `watch` работает, не запускайте `telegram-chats` или другой получатель обновлений этого же бота. При настроенном webhook приём команд работать не будет; приложение его не удаляет.

На один отчёт допускается до 100000 событий и 64 МиБ исходных данных; размер TXT — до 8 МиБ. Поиск контекста реселлеров читает историю потоком, ограничен тайм-аутом, 2 млн строк и 512 МиБ; при превышении лимита частичный результат не выдаётся. Если период слишком большой, файл не отправляется частично: повторите запрос, например `/report 15m`.


После изменения `TELEGRAM_CHAT_ID` или обновления бинарника остановите старый `watch` через `Ctrl+C` и запустите его заново. Существующий `.env` и папку `local/` сохраняйте.

Начальные настройки можно изменить в `.env`:

| Настройка | По умолчанию |
| --- | --- |
| `WATCH_INTERVAL` | `2m`: пауза после завершения цикла и длина свежего окна сбора |
| `WATCH_WINDOW` | `15m`: период предпросмотра `--dry-run` и окно немедленного анализа; не загружает историю при старте |
| `WATCH_REPORT_INTERVAL` | `15m`: интервал отправки сводок заказов |
| `WATCH_REPORT_ONLY` | `true`: без немедленных сообщений о каждом новом проблемном заказе |
| `WATCH_COOLDOWN` | `30m`: пауза уведомлений по одному заказу и виду ошибки |
| `WATCH_ERROR_THRESHOLD` | `3`: порог записей для неизвестных некритических ошибок |
| `WATCH_NO_LOGS_AFTER` | `10m`: проверка отсутствия новых логов |
| `WATCH_DB_FILE` | `local/loki.db`: локальная база, срок хранения 48 часов |

По умолчанию включён `WATCH_REPORT_ONLY=true`: новые ошибки накапливаются в SQLite, сводка отправляется раз в 15 минут. Первая сводка включает только сохранённые данные текущего запуска; следующая начинается с конца предыдущей. Сохранённое расписание продолжает действовать, поэтому первая сводка после запуска может быть короче 15 минут. При неудачной отправке периоды сводки объединяются в пределах текущего запуска. Сбор при этом всегда читает свежее окно, без догрузки из позиции SQLite. Ошибочный запрос не повторяется; следующий цикл снова читает свежее окно. Пропуски после ошибок, сна или перезапуска остаются видны в покрытии. В консоли между сводками виден ход сбора, но сообщения об отдельных заказах в чат не отправляются.

В коротком сообщении — общие счётчики и все категории ошибок. Реселлеры с названием и ID показываются целиком, если список короткий; большой список заменяется их количеством и указанием на TXT. Списка первых пяти заказов больше нет.

`WATCH_REPORT_ONLY=false` возвращает прежний режим немедленных уведомлений. В нём известные ошибки создания и обработки заказа вызывают уведомление сразу. Для остальных сообщений действует критический regex (`fatal`/`critical`) или порог `WATCH_ERROR_THRESHOLD`. «Заказ ещё обрабатывается» не вызывает красное уведомление. Повтор по тому же заказу и виду ошибки ограничен `WATCH_COOLDOWN`. Уведомление показывает все категории текущего периода, а не первые пять заказов из очереди. Пауза повторов влияет на момент отправки, но не вырезает заказы из показанных счётчиков. Недоставленная сводка заменяется свежей после следующего успешного сбора; при сбое Loki устаревший срез не выдаётся за текущий. В обоих режимах технические сообщения о доступе и отсутствии логов идут отдельно при изменении состояния.

`WATCH_INCLUDE_REGEX` и `WATCH_EXCLUDE_REGEX` выбирают ошибки, которые могут вызвать немедленное уведомление; пустые значения отключают фильтры. Содержимое сводки и TXT охватывает все распознанные актуальные ошибки периода, даже если поводом отправки была только одна из них. Regex читаются буквально, значения с пробелами заключайте в кавычки. Пустой `WATCH_CRITICAL_REGEX` включает поиск fatal/critical только в сообщении или текстовом уровне. Свой regex проверяет всю исходную строку; учитывайте возможные совпадения в посторонних полях. Это начальные настройки, их нужно сверить с обычным потоком сервиса.

В шапке — уникальные заказы за период: всего, успешно обработаны, с ошибкой и без известного результата. Ниже такая же разбивка по `new`, `renew`, `cancel`; неизвестный или противоречивый тип указан отдельно. Далее — все встреченные категории ошибок и число уникальных заказов каждой категории с разбивкой по типам. Детали по реселлерам и все ID заказов доступны по кнопкам в TXT; первые пять заказов больше не подменяют общую картину. Ошибки без ID заказа считаются отдельно.

Успешная обработка подтверждается сообщением `order provisioned`. Оно снимает только более ранние ошибки этого заказа, в том числе ещё не доставленные в Telegram. Ошибка после подтверждения снова считается актуальной; при равном времени успех не предполагается. `order created`, `order items provisioned` и успешное чтение заказа не заменяют подтверждение. Это результат наблюдаемой обработки, а не гарантия дальнейшего бизнес-результата. Заказы без подтверждения и без актуальной ошибки остаются в категории «результат неизвестен».

Подтверждение успеха и тип читаются до пользовательских фильтров; фильтр ошибок не скрывает успешное завершение. Сводка рассчитывается только за указанные в ней границы; часовой и двухчасовой TXT запрашиваются отдельно. Все данные берутся из реально собранного архива, поэтому два часа в запросе не означают, что приложение уже успело собрать два часа логов. Числовой уровень лога сам по себе не определяет ошибку. Отсутствие логов оценивается по исходным сохранённым событиям **до фильтров**, только когда весь период `WATCH_NO_LOGS_AFTER` подтверждён; проблемы подключения и неполный сбор показываются отдельно.

### Как видеть полноту и доставку

- После завершения каждого цикла выдерживается пауза 2 минуты. Конец окна — текущее время минус 10 секунд; начало — `max(SessionStart, конец − WATCH_INTERVAL)`. По умолчанию это свежее окно до 2 минут, без дополнительного перекрытия. Каждая полная часть сразу сохраняется; страницы и успешные неполные ответы дочитываются или дробятся в пределах текущего окна и бюджета: по умолчанию 30 секунд и не более 64 вызовов сборщика.
- Ошибочный запрос автоматически не повторяется; неполученный участок остаётся пробелом. Следующий цикл вычисляет свежее окно независимо от сохранённой позиции SQLite. Старые пропуски не догружаются даже после сна без перезапуска процесса.
- Время запросов и обработки добавляется к паузе и может создавать промежутки между окнами; поздние события тоже могут не попасть в архив. Режим показывает текущую тенденцию ошибок, а не гарантированно полную историю. Предпросмотр ограничен 100000 записями и 64 МиБ содержимого; при превышении он сообщает об ошибке.
- Сводка раз в 15 минут обычно охватывает около 15 минут с конца предыдущей сводки. Начало ограничено текущим запуском; первая сводка может быть короче. При задержке доставки периоды объединяются внутри запуска; ориентируйтесь на границы в шапке.
- «Все участки периода получены» означает подтверждённое покрытие выгрузками. «Неполный сбор» показывает конкретные неподтверждённые участки. У старых записей до обновления покрытия может не быть.
- Отсутствие событий в успешно полученном участке отличается от отсутствия самого участка. Пропуски внутри текущего запуска и время между запусками не выдаются за полную историю.
- В консоли отдельно видны ход сбора, следующий срок сводки и подтверждение отправки Telegram. Ожидающее техническое сообщение может быть отложено паузой уведомлений; оно не означает, что сводка уже готова.

После обновления остановите прежний процесс через Ctrl+C и запустите `./lokictl watch` (из проекта — `./bin/lokictl watch`). Файлы `.env`, базы и состояния сохраните: существующие события, покрытие и расписание не сбрасываются. Для сбора свежего окна новая схема не требуется; при переходе со старой схемы версии 1 таблицы позиции и покрытия добавляются автоматически. Старые бинарники не поддерживают схему версии 2.

### Варианты представления

По умолчанию выбран вариант **по категориям ошибок**: он помогает сразу увидеть, что преобладает — таймауты, отсутствие заказа или другая причина. В сообщении нет списка заказов; если названий/ID реселлеров много, они целиком доступны в TXT.

| Вариант | Сообщение в Telegram | Полный TXT |
| --- | --- | --- |
| По ошибкам — текущий | Общие итоги → категории и количество заказов → короткий список реселлеров либо их число | Итоги → категории → сводка по реселлерам → все заказы по каждой ошибке |
| По реселлерам — возможная альтернатива | Реселлер, его ID и число проблемных заказов → распределение по ошибкам | Реселлер → ошибки → заказы |
| Максимально коротко — возможная альтернатива | Всего заказов, с ошибками и счётчики категорий; реселлеры только в TXT | Текущий полный отчёт без сокращения ID |

Альтернативы описывают возможное оформление, отдельных переключателей для них сейчас нет. В полном TXT компактная сводка расположена перед списком заказов, поэтому его не обязательно читать целиком.

## База и состояние

Обычный `watch` сам создает SQLite-базу по `WATCH_DB_FILE`. В нее до фильтров сохраняются исходная строка целиком, точное время Loki, метки и metadata. Повторное чтение перекрывающегося окна не умножает события; два одинаковых события в исходном ответе остаются двумя.

Хранятся только последние **48 часов по времени Loki**. Старые входящие события не записываются; очистка выполняется при запуске и каждом цикле, даже если Loki недоступен. Когда приложение выключено или компьютер спит, удаление невозможно — оно возобновляется при работе приложения. Каждый цикл собирает свежее окно, не раньше `SessionStart`. `WATCH_WINDOW` не загружает начальную историю; пропуски за пределами свежего окна не догружаются после ошибок, сна или нового запуска. Уже сохранённые события и покрытие прошлых запусков остаются доступны для отчётов до удаления по сроку хранения.

База не шифруется и содержит исходные чувствительные данные. На macOS/Linux файл создается с правами `0600`; на Windows храните его в личной папке без общего доступа. Не отправляйте базу в чат или коллегам. Размер зависит от объема логов за 48 часов; фиксированного лимита в мегабайтах нет. Освободившиеся страницы переиспользуются, файл не обязательно уменьшается сразу.


Проверка базы без токенов Loki и Telegram:

```sh
./lokictl db-status
./lokictl db-cleanup --timeout 2m
```

Обе команды создают базу при отсутствии, очищают записи старше 48 часов и показывают статистику; `db-status` тоже изменяет базу. Доступны `--env-file` и `--timeout`. Путь `WATCH_DB_FILE` считается от текущей папки, а не от бинарника.

`local/watch-state.json` хранит интервалы уведомлений и недоставленные сообщения. Запись заменяется целиком; после рестарта очередь продолжается. При неоднозначном сетевом таймауте редкий дубль возможен. Не удаляйте состояние для «перезапуска»: это сбросит паузы и очередь.

Файл `.lock` рядом защищает от второго процесса. После аварии удаляйте оставшийся `.lock` только убедившись, что монитор остановлен. При смене источника, проекта или чата выбирайте отдельный `WATCH_STATE_FILE`.

Держите терминал, сеть и VPN включенными. Периодические сводки используют данные SQLite от конца предыдущего отчёта, но не раньше начала текущего запуска; `/report 1h` и `/report 2h` рассчитываются отдельно по всему доступному архиву, включая прошлые запуски и пробелы между ними. Поиск заказа по накопленным данным и команды запроса заказа в боте пока не реализованы.
