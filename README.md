# Loki: логи заказов и уведомления Telegram

**Первый запуск сотрудником:** [QUICKSTART.md](QUICKSTART.md). **Локальный запуск и сборка:** [BUILD.md](BUILD.md). **Передача коллеге:** [spec/distribution.md](spec/distribution.md). **Выполненные задачи и приемка:** [task/README.md](task/README.md).

**Как читать код по порядку:** [CODE_GUIDE.md](CODE_GUIDE.md) — путь от запуска `watch` до сводки и ответа на `/report`.

Приложение на Go собирает логи `sds-orders` через Grafana/Loki, хранит их локально в SQLite и отправляет в Telegram сводки ошибок заказов. Отдельный сервер базы не нужен. Компоненты получают настройки и зависимости из `cmd/lokictl/main.go`.

По умолчанию пауза между циклами сбора — **2 минуты**, а сводка заказов отправляется **раз в 15 минут**. Обычный `watch` каждый раз получает свежее окно последних 2 минут, ограниченное началом текущего запуска (`SessionStart`). Пропуски после ошибок, сна или остановки процесса не догружаются из сохранённой позиции. `WATCH_REPORT_ONLY=true` отключает отдельные уведомления о каждом новом проблемном заказе. Автосводки охватывают сохранённые данные текущего запуска; расписание отправки продолжается, поэтому первая сводка может быть короче 15 минут. Время фактической отправки может сдвинуться на длительность запросов. Во время сна или выключения компьютера сбор не работает.

Конец запросов отстаёт от текущего времени на 10 секунд. Поэтому первый цикл ждёт появления допустимого периода, а первый сбор при стандартных настройках происходит примерно через 2 минуты после запуска. `WATCH_WINDOW=15m` задаёт период предпросмотра `--dry-run` и окно немедленного анализа, а не начальную загрузку истории.

Предупреждения об отсутствии логов или недоступности Loki остаются отдельными и отправляются при изменении состояния. Чтобы вернуть немедленные уведомления об ошибках, задайте `WATCH_REPORT_ONLY=false`; тогда действуют прежние фильтры и пауза повторов `WATCH_COOLDOWN`.

### Сбор и полнота отчёта

В каждом цикле `watch` вычисляет окно заново: конец — текущее время минус 10 секунд, начало — `max(SessionStart, конец − WATCH_INTERVAL)`. При `WATCH_INTERVAL=2m` это последние **2 минуты**, без дополнительного перекрытия. Сохранённая позиция SQLite не определяет начало запросов; очереди старых участков нет. Каждая полная часть и её покрытие сохраняются одной транзакцией; при сбое уже сохранённые части остаются в базе.

Если запрос `FetchLogs` завершился ошибкой, **автоматического повтора нет**: неполученный участок остаётся пробелом. Следующий цикл снова берёт свежее окно, без догрузки старого пропуска. Это действует и после сна компьютера, когда процесс не перезапускался. Чтение страниц и разбиение успешных, но неполных ответов продолжаются только внутри текущего окна и общего бюджета цикла: по умолчанию 30 секунд и не более 64 вызовов сборщика.

Пауза `WATCH_INTERVAL` начинается после завершения работы цикла, поэтому время запросов и обработки может оставлять промежутки между окнами. Запоздавшие события также могут не попасть в архив. Этот режим нужен для наблюдения за текущей тенденцией ошибок и не гарантирует полную историю; известные пробелы показаны в отчётах.

Сводка **раз в 15 минут за предыдущий период** строится только из SQLite; начало периода ограничено началом текущего запуска. При задержках фактический период может быть длиннее, а первая сводка после запуска — короче: границы указаны в сообщении. Telegram и TXT показывают, все ли участки подтверждены. Пустой успешный ответ считается полученным участком; неудачный запрос и ещё не собранное время остаются пробелами. При незавершённом сборе счётчики явно помечаются как неполные. Кнопки и `/report` читают выбранный период всего доступного архива, включая прошлые запуски и пробелы между ними.

Схема SQLite обновляется автоматически с версии 1 до 2; исходные записи сохраняются. Сбор свежего окна не требует новой схемы и не сбрасывает существующие записи, покрытие или состояние уведомлений. Старым записям без учёта покрытия не приписывается полнота. `local/watch-state.json` управляет расписанием и доставкой уведомлений, а покрытие находится в самой базе. Сохранённая позиция остаётся в SQLite, но для догрузки не используется.

Кнопки и команды обслуживаются, пока запущен обычный `watch`. Доступ к отчётам имеет только настроенный `TELEGRAM_CHAT_ID`. Полные исходные логи остаются в SQLite; Telegram получает посчитанные результаты.

**Границы прототипа:** нет REST/UI, `/order`, `/status`, WebSocket, LLM, Kafka и PostgreSQL. Пропуски за пределами свежего окна автоматически не догружаются, в том числе внутри одного запуска; статистической модели аномалий нет. Категории ошибок основаны на известных сообщениях сервиса; прочие сообщения показаны отдельно как нераспознанные. Отсутствие подтверждения обработки не означает падение заказа.

Для команд Loki нужно добавить только `GRAFANA_TOKEN` в локальный файл `.env`. Для отдельной проверки Telegram нужен `TELEGRAM_BOT_TOKEN`. Команда `analyze` не читает `.env` и не требует токенов. Не отправляйте токены в чат и не добавляйте их в Git.

Grafana — веб-интерфейс, в котором вы смотрите логи. Loki — система, где эти логи хранятся. Приложение использует Grafana как посредника: отправляет ей запрос, а она обращается к настроенному источнику Loki.

Адрес запросов имеет вид:

```text
https://grafana.dev.armlab.pro/api/datasources/proxy/uid/ddxh9oc39r6rka/loki/api/v1/...
```

UID — постоянный идентификатор источника данных внутри Grafana, а не его отображаемое имя. Такой путь описан в [официальном API источников данных Grafana](https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/api-legacy/data_source/).

## 2. Как получить токен

Нужен токен служебной учетной записи Grafana — **Service account**. Эта учетная запись используется программой и должна иметь только необходимые права на чтение выбранного источника логов в организации `1`.

Если у вас есть соответствующие права в Grafana, откройте **Administration → Users and access → Service accounts**, выберите или создайте подходящую учетную запись и добавьте токен. Названия разделов могут отличаться между версиями и настройками Grafana. Подробнее: [служебные учетные записи Grafana](https://grafana.com/docs/grafana/latest/administration/service-accounts/).

Если раздел недоступен, попросите администратора предоставить такой токен. Пример запроса:

> Нужен токен служебной учетной записи Grafana в организации 1 для чтения логов через источник Loki с UID ddxh9oc39r6rka. Проект sds-orders. Запись и административные права приложению не нужны.

Личный вход в Grafana через корпоративную учетную запись не означает, что программа сможет войти тем же способом. В этой версии поддерживается только токен; пароль, браузерная сессия и корпоративный вход не используются.

### Локальная база за последние 48 часов

Обычный `watch` автоматически создает SQLite по `WATCH_DB_FILE` (по умолчанию `local/loki.db`). Путь считается от текущей рабочей папки, как `.env`, а не от расположения бинарника. База встроена: сервер и установленная утилита SQLite не нужны. `watch --dry-run`, `logs` и `analyze --file` архив не пополняют.

До фильтрации сохраняются точная исходная строка, timestamp Loki, проект, метки потока и structured metadata. Неизвестные поля JSON остаются внутри строки. Повторная выгрузка перекрывающегося окна не увеличивает счетчики: если источник вернул два одинаковых события, архив сохраняет кратность два, а повтор того же окна не дает четыре. Ошибочный или неполный ответ не объявляется полным снимком.

Срок фиксирован: **48 часов по времени события Loki**, а не по времени записи в базу. Более старые входящие события не добавляются. Очистка запускается при старте и каждом цикле, в том числе при недоступности Loki. После выключения или сна удалить данные некому; срок снова применяется при работе приложения. Каждый цикл получает только свежее окно, не раньше `SessionStart`. Пропуски за его пределами не догружаются ни после ошибки или сна, ни после нового запуска. Уже сохранённые события и покрытие остаются доступны до удаления по сроку хранения.

Проверить и обслужить базу можно без токенов Loki и Telegram:

```sh
bin/lokictl db-status
bin/lokictl db-cleanup --timeout 2m
bin/lokictl db-status --env-file /absolute/path/to/local.env
```

Обе команды открывают базу, при отсутствии создают ее, применяют очистку 48 часов и показывают число событий и границы сохраненного периода. **`db-status` тоже обслуживает базу и не является проверкой только для чтения.** `db-cleanup` дополнительно выводит число удаленных строк хранения. Исходные сообщения эти команды не печатают.

После удаления SQLite переиспользует свободные страницы; постепенное освобождение страниц снижает расход диска без полного `VACUUM` на каждом цикле. Размер файла не обязан уменьшаться сразу и не ограничен фиксированным числом мегабайт: при большом объеме даже 48 часов могут занимать много места. Это срок хранения записей, а не обещание немедленного физического стирания каждого байта.

SQLite-файл не шифруется и может содержать персональные данные и секреты из исходных логов. На Unix он создается с правами `0600`; храните его локально в личной папке, без публикации и отправки в Telegram. В комплект коллеги не входят ни база, ни ее служебные файлы, ни папка `local/`.

`local/watch-state.json` остается отдельной очередью уведомлений и состоянием антиспама; расписание не сбрасывается при новом запуске. В режиме `WATCH_REPORT_ONLY=true` очередная сводка рассчитывается по SQLite за период после предыдущей, но не раньше начала текущего запуска. В режиме немедленных уведомлений (`false`) каждое сообщение описывает последнее окно `WATCH_WINDOW`, также ограниченное текущим запуском. Отчёты по всему доступному архиву, в том числе прошлых запусков, доступны через кнопку периода и `/report`; отдельной команды поиска заказа пока нет. После обновления бинарника остановите прежний `watch` через `Ctrl+C` и запустите заново, сохранив `.env` и `local/`.

### Анализ файла без сети

После сборки можно сразу проверить обработку на демонстрационных данных:

```sh
bin/lokictl analyze --file examples/orders-analysis.txt
bin/lokictl analyze --file examples/loki-query-response.txt
```

[orders-analysis.txt](examples/orders-analysis.txt) — полностью синтетический пример: все идентификаторы вымышлены. В нем два заказа, событие позиции с родительским `orderId`, один известный текст ошибки и одно неизвестное сообщение. В 12 записях показана последовательность: создание первого заказа, ошибка одной операции, затем подтверждение этапа обработки заказа сообщением `order provisioned`. После него отчет сообщает: «Сервис подтвердил выполнение этапа обработки заказа». Ошибка остается в истории. У второго заказа есть только чтение и ответ `order received successfully`: исход его обработки неизвестен. Все сообщения в этом файле учебные; это не состояние ваших заказов.

Ожидаемый результат примера: 12 записей, 2 заказа, у одного подтвержден этап обработки, у второго исход неизвестен; 1 событие ошибки и 1 нераспознанное сообщение. Команда обозначает демонстрационные данные, объясняет состояния по-русски и показывает последние пять событий каждого заказа. Если последняя известная ошибка старше этих пяти событий, она дополнительно выводится отдельно. Связь с реселлером и причины пропуска также подписаны словами. Сырой текст сообщений не печатается, но ID берутся из файла: это не средство обезличивания. Распознаются 14 типов событий; ошибками считаются три точных сообщения из [таблицы правил](spec/processing.md); остальные неизвестные сообщения попадают в причины пропуска. Числовой `level` не используется для определения ошибки: нужны подтвержденные значения уровней.

Состояние описывает найденные в файле события:

- «Этап обработки подтвержден» (`provisioned`) — есть `order provisioned`. Более позднее чтение, промежуточное событие или ошибка отдельной операции не стирают это подтверждение. Полный бизнес-исход заказа пока не определяется.
- «Есть события обработки, подтверждения этапа нет» (`in_progress`) — видна работа с заказом, но в выборке нет `order provisioned`. Обычная обработка сама по себе не является ошибкой; это также не доказательство, что заказ продолжает выполняться сейчас.
- «Исход неизвестен» (`unknown`) — есть только чтение или ошибки без событий обработки. `order received successfully` означает успешное получение заказа при чтении и не подтверждает его выполнение.

Статус из исходного сообщения, например `provision`, сохраняется в модели отдельно от вывода анализатора и не выводится в краткий консольный отчет. Количество ошибок — события отдельных операций, а не число неуспешных заказов. Правила конечного бизнес-успеха, падения, отмены и повторных попыток остаются в [плане](spec/processing.md).

`resellerId` переносится с известных событий на весь заказ с тем же `(project, order_id)`. Если он отсутствует в остальных строках, связь сохраняется. Отсутствующий и конфликтующий реселлеры отмечаются отдельно; такой заказ не попадает в отчет произвольно выбранного реселлера.

Поддерживаются два формата файла; формат определяется автоматически:

- JSON-ответ Loki с `status=success` и `resultType=streams`, как в выводе `logs --raw`. Это один ответ целиком, не построчный JSON. Проект берется из метки потока `app`.
- Текстовый экспорт Grafana из Explore. Нужен заголовок `Common labels: {"app":"sds-orders",...}`; каждая запись содержит три поля через табуляцию: Unix-время в миллисекундах, дату RFC3339 и исходное сообщение. Дата должна совпадать с миллисекундами; сохраняется точность даты. Дополнительные заголовки сводки и `Total bytes processed` допустимы, но не доказывают полноту выгрузки. Общие метки используются для всех записей; отсутствующие индивидуальные метки не восстанавливаются.

Например, сохраненный из браузера файл с пробелами в имени можно передать так:

```sh
bin/lokictl analyze --file "local/Logs export.txt"
bin/lokictl analyze --file "local/Logs export.txt" --all-orders
```

По умолчанию подробно показываются до 10 заказов: сначала с известными ошибками операций, затем остальные без подтверждения этапа, затем остальные заказы. `--all-orders` показывает каждый заказ. Для каждого остаются последние пять событий; общая сводка и сводка реселлеров всегда учитывают весь файл, независимо от лимита показа.

Оба формата ограничены 10 МиБ и 100 000 записями. Ошибка внешнего формата останавливает чтение с указанием причины; некорректные сообщения внутри корректных записей учитываются в причинах пропуска. Настройки Loki на этот режим не влияют. Доступны только `--file`, `--timeout`, `--all-orders` и `--help`. Каждый запуск вычисляет сводку заново и ничего не сохраняет в БД. Метка потока `dataset=synthetic-example` обозначает демонстрационные записи; сценарий `app.AnalysisService` отдельно считает их и предупреждает о смешанной выборке. Он не определяет вымышленность данных по ID и не проверяет достоверность этой метки.

Для собственной выборки сохраните исходный ответ в игнорируемую папку `local`:

```sh
mkdir -p local
umask 077
bin/lokictl logs --since 2m --limit 1000 --raw > local/orders.txt
bin/lokictl analyze --file local/orders.txt
```

Если `logs` вернул код `2`, файл содержит только полученную страницу. Анализ не доказывает полноту истории заказа и не догружает недостающие логи. У текстового экспорта Grafana также может быть лимит строк: выбранный в браузере период не означает, что файл содержит весь этот период. Заголовок сводки экспорта нужно сверять с фактически сохраненными записями. В `watch` полнота текущего окна проверяется отдельно через FetchLogs; это не добавляет отсутствующую историю в файл. Повторяющиеся записи внутри файла учитываются отдельно; повторную загрузку полного окна теперь учитывает SQLite-хранилище в `watch`; анализ отдельного файла по-прежнему сохраняет каждую запись.

### Инициализация Telegram-бота

1. Откройте официальный [@BotFather](https://t.me/BotFather) в Telegram, отправьте `/newbot` и задайте имя и username бота. Если бот уже создан, используйте его токен. [Инструкция Telegram](https://core.telegram.org/bots/features#creating-a-new-bot)
2. Добавьте токен в локальный `.env` в строку `TELEGRAM_BOT_TOKEN=`.
3. Запустите проверку:

```sh
bin/lokictl telegram-check
```

Команда создает клиент, один раз вызывает [Telegram `getMe`](https://core.telegram.org/bots/api#getme) и выводит username и ID бота. После этого приложение завершается. Для этой проверки ID чата не нужен. Отправка уведомлений доступна в `watch`; `telegram-chats` помогает получить ID группы. Ответы на команды `/order` и `/status` пока не реализованы.

Названия реселлеров берутся из `examples/data.json` (путь `RESELLER_MAP_FILE`); уведомления и TXT сохраняют рядом с названием исходный ID. После изменения справочника перезапустите `watch`.

Сводку ошибок из SQLite можно запросить в настроенной группе Telegram командой `/report` (за час), `/report 1h` или `/report 2h`. Пока работает обычный `watch`, бот пришлёт TXT: итоговые счётчики, категории ошибок и сводка по реселлерам (название, ID, число заказов). Далее отдельным разделом идут типы операций и полный список ID затронутых заказов. Ленты событий и ограничения первыми заказами в этом отчёте нет. Порядок запуска и ограничения описаны в [QUICKSTART.md](QUICKSTART.md#подробный-отчёт-в-telegram).

Подключения независимы: `telegram-check` не требует `GRAFANA_TOKEN`, а команды Loki — `TELEGRAM_BOT_TOKEN`. Для проверки бота доступны `--env-file`, `--timeout` и `--help`. Флаги периода, лимита и `--raw` относятся к ручным командам Loki; `--project` доступен также в `watch`.

### Проверка Loki

Метка — пара «имя — значение», по которой Loki находит нужные логи. Например, `app="sds-orders"` выбирает поток логов этого приложения. Список меток и их значений зависит от имеющихся данных; это не каталог всех когда-либо существовавших проектов.

Проверяйте последовательно:

```sh
bin/lokictl labels
bin/lokictl values app
bin/lokictl projects
bin/lokictl logs --since 15m --limit 20
```

Другой проект можно задать для одного запуска:

```sh
bin/lokictl logs --project another-service --since 30m --limit 10
```

Собственный запрос:

```sh
bin/lokictl query --query '{app="sds-orders"}' --since 15m --limit 20
bin/lokictl query --query '{app="sds-orders"} |= "ERROR"' --since 1h --limit 20
```

`|= "ERROR"` ищет указанную подстроку в Loki с учетом регистра. Это фильтр на стороне Loki. В `watch` есть локальные include/exclude regex и отдельное правило критичности; команда `analyze --file` эти фильтры пока не применяет. Запрос должен возвращать записи логов; вычисления метрик этой версией клиента не поддерживаются.

### Период и ограничения

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `--since` | `15m` | Последние 15 минут; допустимы также `30s`, `1h`, `1h30m` |
| `--start`, `--end` | Не заданы | Точные границы периода, обе обязательны |
| `--limit` | `20` | Максимум событий в одном ответе для `logs` и `query`, от 1 до 100 000 |
| `--project` | Из `.env` | Проект для команды `logs` |
| `--query` | Не задан | Обязательное выражение LogQL для команды `query` |
| `--timeout` | `30s` | Максимальное время выполнения команды; больше нуля и не более `10m` |
| `--env-file` | `.env` | Путь к файлу настроек относительно текущей папки |
| `--raw` | Выключен | Вывод исходного успешного JSON-ответа |
| `--help` | — | Краткая справка без сетевого запроса |

Указывайте параметры после команды. Для Loki используйте либо `--since`, либо пару `--start` и `--end`. Максимальный период — 24 часа. Начало периода включается в выборку, конец не включается.

Точная дата указывается с часовым поясом, например `2026-10-09T12:00:00+03:00`; `Z` означает UTC. Допустимы доли секунды. Пример:

```sh
bin/lokictl logs \
  --start '2026-10-09T12:00:00+03:00' \
  --end '2026-10-09T12:15:00+03:00' \
  --limit 20
```

При необходимости замените даты на период, за который в Loki есть данные.

### Как увидеть исходные логи

Обычный вывод `logs` и `query` показывает сведения о результате без текста сообщений. Для просмотра исходного ответа включите `--raw` явно:

```sh
bin/lokictl logs --since 5m --limit 5 --raw
```

Этот режим выводит JSON — текстовый формат обмена данными, полученный от Loki. В нем могут быть персональные данные, токены и другие секреты из логов. Очистка и маскирование исходного ответа сейчас не реализованы. Не публикуйте такой вывод и не отправляйте его в LLM без отдельной подготовки.

Если число событий достигло `--limit`, выборка **может быть неполной**. Это не доказывает, что существуют дополнительные записи, но считать выгрузку полной уже нельзя. Команда не догружает остальное. Пустой успешный ответ означает, что запрос не вернул событий за выбранный период; ошибка доступа или сети сообщается отдельно.

Коды завершения: `0` — команда выполнена, `1` — ошибка, `2` — получена страница, достигшая лимита. Код `0` у `check` подтверждает доступ к списку меток, а не наличие логов конкретного проекта. Результат выводится в стандартный вывод (`stdout`), ошибки и предупреждение о лимите — в поток диагностики (`stderr`). Нажатие Ctrl+C отменяет активный запрос.

## 5. Настройки

| Переменная | Назначение |
| --- | --- |
| `GRAFANA_URL` | Базовый адрес Grafana, без `/explore` и без параметров страницы |
| `GRAFANA_DATASOURCE_UID` | UID источника Loki в Grafana |
| `GRAFANA_ORG_ID` | Идентификатор организации Grafana |
| `GRAFANA_TOKEN` | Токен служебной учетной записи; обязателен для команд Loki |
| `LOKI_PROJECT` | Проект по умолчанию для `logs` и `watch` |
| `LOKI_PROJECT_LABEL` | Имя метки проекта, в этой настройке `app` |
| `TELEGRAM_BOT_TOKEN` | Токен для `telegram-check`, `telegram-chats` и отправки из `watch` |
| `TELEGRAM_CHAT_ID` | Числовой ID выбранной группы или чата для отправки |
| `WATCH_DB_FILE` | Путь SQLite, по умолчанию `local/loki.db` |
| `WATCH_STATE_FILE` | Состояние доставки и антиспама, по умолчанию `local/watch-state.json` |
| `WATCH_INTERVAL` | Пауза после завершения цикла и длина свежего окна сбора: `2m` |
| `WATCH_WINDOW` | Период предпросмотра и окно немедленного анализа `15m`, без загрузки истории при старте |
| `WATCH_REPORT_INTERVAL`, `WATCH_COOLDOWN` | Период сводки `15m`; пауза повторов `30m` применяется в режиме немедленных уведомлений |
| `WATCH_ERROR_THRESHOLD`, `WATCH_NO_LOGS_AFTER` | Порог повторов `3` и контроль отсутствия логов `10m` |
| `WATCH_REPORT_ONLY` | `true`: периодические сводки; `false`: также немедленные уведомления об ошибках |
| `WATCH_INCLUDE_REGEX`, `WATCH_EXCLUDE_REGEX`, `WATCH_CRITICAL_REGEX` | Локальные фильтры и правило критичности; подробности в QUICKSTART |

Для сетевых команд программа читает `.env` сама. `analyze` полностью пропускает загрузку настроек подключения. Формат простой: одна пара `ИМЯ=значение` в строке. Допустимы пустые строки, комментарии отдельной строкой с `#` и значения в одинарных или двойных кавычках. Содержимое кавычек трактуется буквально. Файл не является shell-скриптом: команды, подстановка `$VARIABLE`, `$(...)`, префикс `export` и комментарии после значения не поддерживаются.

Неизвестные и повторяющиеся имена настроек считаются ошибкой. Максимальный размер файла — 64 КиБ. Отсутствие стандартного `.env` допустимо, если настройки заданы в окружении; явно указанный через `--env-file` файл должен существовать.

Переменные, уже заданные в окружении процесса, имеют приоритет перед файлом, в том числе пустые. Если исправление `.env` не изменило поведение, проверьте, не задана ли одноименная переменная в терминале. Значение токена выводить для проверки не нужно.

Альтернативный файл:

```sh
bin/lokictl check --env-file /absolute/path/to/local.env
```

## 6. Как сверить настройки с Grafana

1. Откройте Grafana в браузере. Ее базовый адрес — часть URL до пути страницы: например, `https://grafana.dev.armlab.pro`.
2. Перейдите в **Explore**, выберите источник Loki и выполните рабочий запрос проекта `sds-orders`.
3. Откройте **Query inspector → Query**. При необходимости нажмите **Refresh**. Здесь видны запрос и ответ; по ним можно сверить источник и выражение LogQL. [Инструкция Grafana](https://grafana.com/docs/grafana/latest/visualizations/explore/explore-inspector/)
4. Если инспектор показывает `/api/ds/query`, не копируйте этот адрес в `GRAFANA_URL`: это другой способ обращения Grafana к источнику. Для приложения нужны базовый адрес Grafana и UID источника.

Успешный запрос в браузере подтверждает доступ вашей личной сессии. Токен служебной учетной записи проверяется отдельно командой `check`. Если метка проекта называется иначе, чем `app`, измените `LOKI_PROJECT_LABEL` после проверки списка меток.

## 7. Если что-то не работает

| Результат | Что проверить |
| --- | --- |
| Токен не задан | Заполнен ли `.env`, верна ли текущая папка и не перекрыта ли переменная пустым значением окружения |
| HTTP 401 | Токен действителен, не истек и принадлежит нужной Grafana |
| HTTP 403 | У служебной учетной записи есть права чтения выбранного источника в организации `1` |
| HTTP 302 или другое перенаправление | Указан адрес API нужной Grafana, а шлюз не отправляет программу на страницу корпоративного входа |
| HTTP 404 | Верны базовый адрес, UID источника и доступность пути проксирования в этой установке |
| HTTP 400 | Корректен LogQL, существует выбранная метка, допустимы период и лимит для сервера |
| Тайм-аут или ошибка соединения | Доступна сеть/VPN; затем при необходимости увеличьте `--timeout` |
| Пустая выборка | Есть события в этом периоде и верны имя метки, проект и условие запроса |
| Неверный JSON | По адресу возвращается Loki API, а не HTML-страница входа или ответ другого сервиса |

Программа проверяет HTTPS-сертификат и не следует перенаправлениям автоматически. Она не печатает токен и тело ошибочного ответа сервера. Для диагностики можно передать администратору код HTTP и название команды; секреты для этого не нужны.

Для `telegram-check` проверьте заполнение `TELEGRAM_BOT_TOKEN` и доступность `api.telegram.org`. При отклоненном токене проверьте его в BotFather. Токен Telegram входит в путь запроса, поэтому клиент скрывает адрес и исходную сетевую ошибку в диагностике.

## 8. Как устроен код

Основной сценарий `watch` управляется пакетом `monitor`: он запускает сбор, сохраняет логи, рассчитывает сводки и организует доставку в Telegram. `cli` разбирает команду запуска и флаги. Пакет `app` обслуживает отдельные ручные команды Loki и анализ файла; в рабочем пути `watch` он не участвует. Все компоненты создаются и соединяются в [cmd/lokictl/main.go](cmd/lokictl/main.go); отдельного слоя сборки и контейнера DI нет.

```text
cmd/lokictl/main.go    # Запуск, конфигурация и соединение компонентов
internal/
  cli/
    cli.go            # Выполнение ручных запросов Loki и анализа файла через app
    options.go        # Аргументы, проверка параметров и справка
    output.go         # Оформление ответов CLI
  app/
    service.go        # Сценарии получения логов и анализа файла
    models.go         # Запрос ручной команды Loki и его проверка
  config/config.go    # Настройки, чтение .env и проверка
  loki/
    client.go         # HTTP-запросы к Loki и разбор ответа
    logs.go           # Запрос страницы, построение LogQL и выгрузка периода
    models.go         # Параметры запроса, настройки и ограничения клиента
  input/file.go       # Чтение JSON Loki и TXT Grafana
  analyzer/analyzer.go # Правила событий и сборка истории заказов
  model/
    loki.go           # Ответ Loki, записи и полнота выгрузки
    order.go          # Сообщение приложения, события и состояния заказов
    telegram.go       # Бот, сообщения и нажатия кнопок Telegram
  monitor/            # Основной цикл watch, анализ сохранённых логов, сводки и доставка
  storage/            # SQLite: события, повторы окон, очистка и контекст реселлеров
  report/text.go      # Подробности CLI и сгруппированный отчёт ошибок для Telegram
  telegram/
    client.go         # Запросы Bot API и отправка TXT
    reports.go        # /report и кнопка периода, доступ к чату и защита от повторов
  utils/http.go       # HTTP-клиент с тайм-аутом и запретом редиректов
tests/
  cli/                # Команды, аргументы и терминальный вывод
  app/                # Сценарии с переданными тестовыми зависимостями
  config/             # Настройки и .env
  loki/               # Запросы к тестовому HTTP-серверу
  input/              # Чтение файлов
  analyzer/           # События и истории заказов
  model/              # Разбор внешних моделей
  telegram/           # Bot API, документы и обработка /report
  report/             # Формат TXT и ограничение размера
  monitor/            # Цикл, фильтры и доставка уведомлений
  storage/            # SQLite, повторные окна и срок хранения
  utils/              # Настройки общего HTTP-клиента
  integration/        # Запуск программы и соединение компонентов
examples/
  loki-query-response.txt # Реальный JSON-ответ: 2 потока, 5 записей
  orders-analysis.txt    # Синтетический ответ: 2 заказа, 12 записей
  data.json              # Справочник ID → название реселлера
spec/                 # План обработки, хранения и REST API
go.mod, go.sum        # Версия Go и закрепленные зависимости, включая SQLite
.env.example          # Образец настроек без токенов
README.md             # Эта инструкция

```

Все тесты находятся в `tests/`, отдельно от рабочего кода. Файлы объединены по понятной обязанности; для маленьких функций и конструкторов отдельные файлы не нужны. Общие данные лежат в `model`, настройки конкретного компонента — рядом с ним. В `utils` попадают только общие технические функции, без логики заказов.

### Как соединяются компоненты

`main` читает настройки, создает объекты и передает их друг другу. Это и есть внедрение зависимостей, или DI. Компонент использует готовую зависимость через небольшой интерфейс и не создает ее внутри себя.

Для запуска основного сценария:

```text
main.run: cli.Parse → runMonitor → monitor.New → RunWithCommands
                                                ├─ цикл сбора и сводок
                                                └─ telegram.RunReports: /report и кнопки
```

CLI нужен, чтобы запустить `watch` и выбрать его параметры. После запуска `/report` принимает `telegram.RunReports` через Bot API: эта команда не передаётся в `cli.Parse` или `app.Service`. В `--once` и `--dry-run` обработчик команд Telegram не запускается.

Для отдельных ручных команд Loki:

```text
main: config.Load → HTTP-клиент → loki.New → app.New → cli.Run
```

`loki.New` получает только настройки подключения и HTTP-клиент. `app.New` получает настройки проекта и источник логов. `cli.Run` получает сервис, параметры команды и потоки вывода. Токен не передается в анализатор или форматирование отчета.

Для локального анализа соединение видно в трех строках:

```go
source := input.NewLokiFileSource()
service := app.NewAnalysisService(source, analyzer.New())
return cli.RunAnalysis(ctx, service, options, output, diagnostic)
```

Этот путь не читает `.env` и не создает сетевые клиенты. Анализатор получает записи и возвращает результат; он не знает о файле, Loki или SQLite. Сервис работает с интерфейсами `RecordSource` и `OrderAnalyzer`, поэтому источник записей и анализатор можно проверить независимо.

Для `telegram-check` точка входа создает `telegram.Client` с токеном и HTTP-клиентом, вызывает `GetMe` и передает результат в `cli.PrintBotInfo`. Отдельный сервис для одного проверочного запроса не требуется. Для `watch` main создает SQLite-хранилище и передает монитору зависимости получения, хранения и отправки. В режиме `--dry-run` хранилище и отправитель не используются. `Analyze` в monitor — чистая обработка окна, а цикл и сохранение состояния отделены от нее.

Для мониторинга и подробностей путь такой:

```text
Loki → SQLite: свежее окно последних 2 минут, пауза 2 минуты после цикла, не раньше запуска
SQLite → monitor: расчёт периода каждые 15 минут → Telegram: сводка + кнопки
Кнопка или /report → SQLite: выбранный период + история реселлеров
                  → monitor: подсчёт → report: TXT → Telegram
```

Сначала полный ответ записывается в SQLite, затем анализируется. Обогащение реселлера не добавляет старые ошибки или старые заказы в счётчики периода. Отправка, получение, хранение и форматирование остаются отдельными компонентами; в тестах их можно подменять независимо.

SQLite работает локально внутри процесса. Возможные PostgreSQL и REST подключаются через отдельные компоненты; сейчас они не реализованы. Добавление LLM позднее не потребует менять получение логов или подсчет событий.

### В каком порядке читать код

Подробный маршрут с функциями и переходами — в [CODE_GUIDE.md](CODE_GUIDE.md). Для обычного `watch` начните так:

1. [cli/options.go](internal/cli/options.go) и [main.go](cmd/lokictl/main.go) — разбор `watch`, выбор сценария в `run` и создание компонентов в `runMonitor`.
2. [monitor/models.go](internal/monitor/models.go) и [monitor/monitor.go](internal/monitor/monitor.go) — зависимости, `RunWithCommands`, цикл и выбор времени сводки.
3. [monitor/collection.go](internal/monitor/collection.go), [loki/logs.go](internal/loki/logs.go) и [storage/coverage.go](internal/storage/coverage.go) — получение свежего окна и сохранение полных частей с покрытием.
4. `databaseSnapshot` в [main.go](cmd/lokictl/main.go) и [monitor/analyze.go](internal/monitor/analyze.go) — чтение периода из SQLite, подсчёт заказов и контекст реселлера.
5. [monitor/monitor.go](internal/monitor/monitor.go) и [monitor/state.go](internal/monitor/state.go) — подготовка сообщения, очередь доставки и её JSON-состояние.
6. [telegram/reports.go](internal/telegram/reports.go), [report/text.go](internal/report/text.go) и [telegram/client.go](internal/telegram/client.go) — приём `/report` и кнопок, создание TXT и отправка в Telegram.

Ручные запросы Loki и `analyze --file` изучайте отдельной веткой: [cli/cli.go](internal/cli/cli.go) → [app/service.go](internal/app/service.go). Анализ файла затем проходит через [input/file.go](internal/input/file.go) и [analyzer/analyzer.go](internal/analyzer/analyzer.go); это другой сценарий, чем анализ сохранённого периода в `monitor`.

Исходный ответ Loki содержит текст, метки потока и metadata. Текущий анализатор извлекает только известные поля и не переносит полный контекст в `OrderEvent`. В `watch` эти исходные данные сохраняются отдельно в SQLite до фильтрации. Неизвестные JSON-поля остаются в точном тексте строки; найденные pod, сервер и остальные метки не заменяются ограниченной моделью `OrderEvent`.

### Пример ответа и два слоя JSON

В [examples/loki-query-response.txt](examples/loki-query-response.txt) находится ответ команды `logs --since 2m --limit 5 --raw`, предоставленный для этого проекта. Приглашение терминала и предупреждение о лимите удалены; JSON и значения событий сохранены. Файл можно открыть обычным редактором или использовать в тестах без токена и доступа к Grafana. Это реальный пример с идентификаторами и метками окружения, а не обезличенные демонстрационные данные.

У ответа два отдельных слоя:

```text
LokiQueryResponse                 внешний ответ Loki
  Data.Result[]                   потоки с одинаковыми метками
    Labels                        метки потока: app, pod и другие
    Values[]                      события потока
      TimestampNS                 время события Loki в наносекундах
      Line                        исходный текст сообщения
        ParseOrderLog(Line)       разбор JSON приложения при необходимости
          OrderLog                поля сообщения sds-orders
```

Внешний ответ описан в [internal/model/loki.go](internal/model/loki.go):

| JSON | Поле Go | Смысл |
| --- | --- | --- |
| `status` | `LokiQueryResponse.Status` | Статус ответа, в примере `success` |
| `data.resultType` | `LokiQueryData.ResultType` | Тип результата; клиент поддерживает `streams` |
| `data.result` | `LokiQueryData.Result` | Список потоков `[]LokiStream` |
| `result[].stream` | `LokiStream.Labels` | Произвольные метки потока `map[string]string` |
| `result[].values` | `LokiStream.Values` | Список событий `[]LokiEntry` |
| `values[][0]` | `LokiEntry.TimestampNS` | Строка с целым числом наносекунд Unix, преобразуемая в `int64` без `float64` и потери точности |
| `values[][1]` | `LokiEntry.Line` | Текст сообщения; Loki не требует, чтобы этот текст был JSON |
| `values[][2]` | `LokiEntry.Metadata` | Необязательные структурированные метаданные `map[string]string`; в примере отсутствуют |
| `data.stats` | `LokiQueryData.Stats` | Статистика запроса, сохраненная целиком как `json.RawMessage` |

У `LokiEntry` собственный разбор JSON, потому что Loki передает событие массивом `["timestamp", "line"]`, а не объектом с именованными полями. Статистика пока не участвует в обработке, поэтому отдельные типы для ее многочисленных внутренних счетчиков не вводятся. В примере `totalLinesProcessed=1742` — число обработанных Loki строк, а `totalEntriesReturned=5` — число возвращенных событий. Это разные счетчики: приложение получило пять событий в двух потоках.

`model.Response.Body` хранит исходное тело успешного ответа для `--raw`. После `QueryRange` поле `model.Response.Query` содержит разобранный `*model.LokiQueryResponse`; для других операций оно не заполняется. `model.Response.Values` содержит уже разобранный список меток или их значений, поэтому CLI не декодирует ответ повторно. Разбор ответа не меняет исходный JSON. Общие `LogRecord` используются при дальнейшем получении и обработке записей, а `FetchResult` отдельно сообщает о полноте выгрузки.

Внутри `Line` у предоставленных событий находится еще один JSON. Его модель описана в [internal/model/order.go](internal/model/order.go). Для других сервисов строка может иметь другой формат: сетевой клиент не пытается автоматически превращать ее в заказ.

| JSON сообщения | Поле Go | Значение и ограничения |
| --- | --- | --- |
| `level` | `Level *int` | Числовой уровень; в примере `30`, текстовое название уровня пока не назначается |
| `time` | `TimeMS *int64` | Время приложения в миллисекундах Unix; оно может отличаться от времени Loki |
| `context` | `Context string` | Контекст приложения, в примере `orders` |
| `id` | `ID string` | ID сущности события: это может быть заказ или его позиция |
| `orderId` | `OrderID string` | Явная ссылка на родительский заказ, когда поле присутствует |
| `type` | `Type string` | Тип заказа, в примере `new` |
| `items` | `Items []OrderItem` | Позиции заказа; наблюдаемое поле позиции — `TariffID` (`tariffId`) |
| `ownerId`, `resellerId` | `OwnerID`, `ResellerID string` | Идентификаторы владельца и реселлера |
| `endTime` | `EndTime json.RawMessage` | В примере только `null`; будущий тип значения пока неизвестен |
| `status` | `Status string` | Исходный статус приложения, в примере `provision` |
| `msg` | `Message string` | Описание события: например, `creating order` |

Поля сообщения необязательны. Указатели для `Level` и `TimeMS` отличают отсутствие значения от числового нуля. `EndTime` различает отсутствующее поле (`nil`) и явный JSON `null`. Неизвестные поля при разборе `OrderLog` пропускаются и остаются в исходной строке `Line`.

`ParseOrderLog` проверяет, что строка является JSON-объектом с допустимыми типами известных полей. Функция не определяет, является ли объект бизнес-событием заказа: даже `{}` — допустимый объект. Классификацию известных сообщений и объединение в историю выполняет отдельный пакет `analyzer`.

Пример содержит последовательность сообщений `creating order`, `create order item`, `sending order to provision`, `order created`, `getting order`. У события `create order item` поле `id` относится к позиции, а `orderId` ссылается на заказ. Поэтому нельзя группировать все записи только по `id` или считать общий `context=orders` достаточным признаком одной сущности. Модель сохраняет оба поля отдельно; анализатор использует таблицу правил из [spec/processing.md](spec/processing.md).

Статус `provision` и сообщение `order created` в этом фрагменте не доказывают успешное завершение всего заказа. Здесь нет примеров ошибки или конечного результата обработки, поэтому состояния «успех» и «падение» из него не выводятся.

### Как прочитать пример без сети

Фрагмент для Go-кода внутри этого проекта; `path` — путь к `examples/loki-query-response.txt`:

```go
import (
    "encoding/json"
    "fmt"
    "os"

    "loki-analyzer/internal/model"
)

func printExampleMessages(path string) error {
    body, err := os.ReadFile(path)
    if err != nil {
        return err
    }
    var response model.LokiQueryResponse
    if err := json.Unmarshal(body, &response); err != nil {
        return err
    }
    for _, stream := range response.Data.Result {
        for _, entry := range stream.Values {
            event, err := model.ParseOrderLog(entry.Line)
            if err != nil {
                return err
            }
            fmt.Println(event.Message)
        }
    }
    return nil
}
```

Так отдельно проверяются внешняя модель Loki и модель сообщения приложения. Пример не делает запросов и не сохраняет логи на диск. `ParseOrderLog` вызывается анализатором в команде `analyze`; команды получения данных сохраняют прежнее поведение.

### Один запрос и полная выгрузка — разные операции

Команды `logs` и `query` используют `QueryRange`: получают одну страницу и сообщают о достижении лимита. Это удобно для проверки подключения и формата реальных данных.

В клиенте отдельно предусмотрен `FetchLogs` для ограниченной выгрузки проекта с разбиением периода. Если ответ заполнил страницу, период делится на два непересекающихся интервала. Предварительный усеченный ответ отбрасывается, чтобы не посчитать записи повторно. Сдвига от последнего события на одну наносекунду нет: разные события могут иметь одинаковое время.

`FetchLogs` возвращает `Complete` и `Reason`: удалось ли завершить выгрузку и почему она остановлена. Метод используется в `watch`; ручные `logs` и `query` остаются одностраничными. Нельзя считать один успешный ответ `QueryRange` полной выгрузкой, а `Complete` — гарантией неизменности истории: в Loki могут поступать запоздавшие записи.

Ограничения клиента по умолчанию: 10 МиБ на один ответ, 64 МиБ на операцию получения, 100 000 записей, 1 000 запросов, 24 часа на период. Для `FetchLogs` страница содержит до 1 000 событий. Эти пределы заданы в `DefaultConfig`; CLI дополнительно задает лимит одной страницы и время ожидания. Ошибки, отмена и достижение пределов обрабатываются явно.

## 9. Как дополнять проект

Изменяйте компонент, который отвечает за новое поведение, и обновляйте тесты и README вместе с ним.

- **Новая операция Loki API.** Реализуйте запрос и разбор ответа в `internal/loki`. Если операция нужна сервису, добавьте ее в `app.LogSource` и вызов в `app.Service`. Для новой консольной команды измените разбор аргументов и вывод в `internal/cli`.
- **Новая настройка.** Добавьте чтение и проверку в `internal/config`, опишите значение в `.env.example` и README. Передайте настройку нужному компоненту в `cmd/lokictl/main.go`; не читайте окружение внутри клиента или сервиса.
- **Другой источник логов.** Создайте адаптер с методами `app.LogSource` и передайте его в `app.New` при сборке приложения. Это не требует менять формат консольного вывода.
- **Другой вывод или интерфейс.** Оформляйте результат в соответствующем интерфейсе: CLI, будущем HTTP API или боте. Сервис получает типизированный запрос и возвращает модель, без печати и чтения пользовательского ввода.
- **Новое событие заказа.** Добавьте подтвержденное правило в `internal/analyzer`, локальный пример и тест. Сначала уточните, что означает сообщение и какое поле содержит ID заказа; не выводите конечный успех или падение из похожего текста.
- **История и база.** `watch` пишет полные исходные события свежего окна в SQLite со сроком хранения 48 часов; сохранённые данные предыдущих запусков остаются в архиве до истечения срока. Дальше можно добавить чтение истории по заказу и анализ накопленных данных. Догрузка пропусков не выполняется; отдельные позиции анализа и PostgreSQL не реализованы, Kafka не используется. SQL остается в `storage`, а порядок получения, записи и уведомления — в сценарии монитора.
- **Уведомления Telegram.** Клиент уже можно создать и проверить. Отправка находится в `internal/telegram`, решение об уведомлении и антиспам — в `internal/monitor`. ID получателя передается через `TELEGRAM_CHAT_ID`.
- **LLM-анализ.** Позднее добавьте отдельный компонент после локальной обработки. Он получает ограниченную сводку с очищенными примерами. Подключение провайдера и его настроек выполняется при сборке приложения; правила подсчета и состояния заказов не зависят от LLM.

Для будущих компонентов сейчас нет пустых пакетов, заглушек или универсальных интерфейсов. Новые зависимости вводятся вместе с конкретной функцией.

Текущая последовательность разработки:

1. Проверить доступ и запросы к реальной Grafana через существующие команды.
2. Проверить существующий локальный анализ через `analyze --file` и дополнить примеры конечными результатами `sds-orders`.
3. Использовать SQLite-архив текущего `watch`: проверить запись, повторное окно и очистку; приемка описана в [task/sqlite.md](task/sqlite.md).
4. Добавить поиск заказа и анализ уже накопленной истории, сохранив сбор свежего окна без догрузки пропусков.
5. Проверить `watch` в целевой группе и передать сборку сотруднику; REST и админка подключаются позже.
6. При необходимости добавить LLM-анализ подготовленной сводки.

## 10. Проверка изменений

Из папки проекта:

```sh
gofmt -w cmd internal tests
go test ./...
go vet ./...
go test -race ./...
go build -o bin/lokictl ./cmd/lokictl
```

Тесты собраны в `tests/<компонент>` и проверяют публичные функции компонентов. Их можно запускать отдельно, без рабочих токенов и запросов к внешним сервисам:

```sh
go test ./tests/config      # Файлы настроек и подстановка окружения
go test ./tests/app         # Сценарии с тестовыми зависимостями
go test ./tests/analyzer    # События, состояния и отчеты по реселлерам
go test ./tests/input       # Чтение файла, формат ответа и лимиты

go test ./tests/telegram    # Telegram через внедренный тестовый HTTP-клиент
go test ./tests/monitor     # Цикл и уведомления
go test ./tests/storage     # SQLite, повторы и очистка
go test ./tests/utils       # Тайм-аут и запрет перенаправлений HTTP
go test ./tests/integration # Запуск CLI и соединение компонентов
```

Тестовый источник реализует `app.LogSource`, тестовый исполнитель — `cli.Executor`. Благодаря передаче зависимостей тесты сервиса и CLI не поднимают HTTP-сервер. Клиент отдельно проверяется через локальный сервер `httptest`.

Тесты моделей читают `examples/loki-query-response.txt` и проверяют разбор внешнего ответа и сообщений приложения, точность времени и раздельное сохранение ID заказа и позиции. Их можно запустить отдельно:

```sh
go test ./tests/model
```

Успешные тесты не подтверждают доступ к внешним сервисам. Рабочие токены проверяются отдельно через `bin/lokictl check` и `bin/lokictl telegram-check`.

Описание конечных адресов и параметров Loki: [Loki HTTP API](https://grafana.com/docs/loki/latest/reference/loki-http-api/).
