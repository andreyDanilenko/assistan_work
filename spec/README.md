# План прототипа мониторинга заказов по логам

Долгосрочный план; исходная фиксация на 10 октября 2026 года. Цель — превратить логи `sds-orders` в историю заказов, понятные состояния и график успешных и неуспешных завершений. Сервис получает данные из Loki каждые две минуты, сохраняет результат обработки и предоставляет его админке через REST. При обнаружении аномалии отправляет уведомление в Telegram.

`[x]` означает реализованное или подтвержденное поведение; `[ ]` — предстоящую работу. Невыполненные пункты и явно обозначенные будущие команды/модели являются требованиями, а не доступными возможностями приложения.

- [Правила обработки и хранения](processing.md) — события, заказы, повторные выгрузки, агрегация и аномалии.
- [План REST API](rest-api.md) — ручки, контракты, безопасность и проверка.
- [README проекта](../README.md) — установка, действующие команды и устройство кода.

## Исходный план

Первоначальный замысел сохраняется: небольшой сервис на Go для получения, фильтрации и агрегации логов без LLM. Он должен сокращать объем повторяющейся информации и оставаться понятным для дальнейшего развития.

| Исходное требование | Текущее состояние |
| --- | --- |
| Получать проекты и логи из Loki | Реализован клиент; доступ через Grafana проверен пользователем |
| Разделить получение, обработку, модели и интерфейс | Выделены получение, локальный анализатор, модели и CLI |
| Фильтровать по уровню, подстроке, regex, email, userID и URL | Сейчас можно задать LogQL вручную; локальные фильтры не реализованы |
| Схлопывать ошибки в шаблон, количество и 1–2 примера | Не реализовано |
| Выбирать проект и период, получать консольную сводку | Получение через CLI-флаги; `analyze --file` показывает заказы, ошибки и реселлеров в сохраненном ответе |
| Оставить возможность подключить UI, Telegram и позднее LLM | Telegram: `getMe`, обнаружение чата и `watch`; входящие команды и остальные интерфейсы предстоят |

План уточнен вокруг заказов: кроме групп ошибок нужна последовательность событий каждого заказа. Для нее нельзя заранее оставить только `ERROR`: сообщения о создании и успешном завершении также нужны. Интерактивное меню CLI не требуется для прототипа; существующих команд и флагов достаточно.

## Принципы реализации

- Простые функции и структуры Go; отдельные пакеты по ответственности, без фреймворка и контейнера DI.
- Настройки читаются один раз в точке входа `cmd/lokictl/main.go`; там же создаются независимые компоненты и явно передаются друг другу. Отдельный слой сборки зависимостей не нужен.
- Анализатор не обращается к сети и БД. Клиенты не принимают решения о состоянии заказа или отправке уведомления.
- CLI и REST используют общие сценарии приложения. Интерфейсы вводятся у потребителя по мере появления реальной зависимости.
- Ошибки и неполные данные видны пользователю. Повторный сбор не увеличивает счетчики уже сохраненных событий.
- Секреты не попадают в Git, диагностические сообщения, REST или Telegram. Примеры логов для интерфейсов очищаются.

LLM не определяет базовые счетчики и состояния заказов. Пустые пакеты и универсальные расширения заранее создавать не нужно. Ближайший шаг — сохранить полный контекст событий в PostgreSQL, проверить один цикл сбора и восстановление, затем включить регулярный сбор.
