# Требования к обработке логов и заказов

Документ описывает локальный анализатор и целевое поведение прототипа с PostgreSQL. Первая версия `watch` — отдельный ограниченный монитор свежего окна с JSON-состоянием; ее действующие правила и ограничения описаны в [QUICKSTART](../QUICKSTART.md). Сейчас доступны события, история заказов, состояния `unknown`/`in_progress`/`provisioned`, счетчики известных ошибок и сводка по реселлерам. Хранение, конечные исходы, агрегация ошибок, сборщик и аномалии еще не реализованы. Порядок работ — в [основном плане](README.md).

## Поток данных и границы слоев

```text
Планировщик или CLI
  → сценарий сбора в app
  → loki.FetchLogs
  → storage: исходные события и позиция сбора в PostgreSQL

CLI или планировщик анализа
  → app: чтение сохраненных событий
  → analyzer: события, состояния, группы ошибок
  → storage: результаты и отдельная позиция анализа

REST → сценарии чтения в app → storage
Сценарий аномалий → очередь в storage → telegram
```

`main.go` создает компоненты и явно передает их зависимости. `model` содержит общие структуры без HTTP, SQL и чтения окружения. `analyzer` применяет свои правила к переданным записям и возвращает результат без побочных действий. Слой `app` управляет порядком действий и транзакциями через небольшие интерфейсы; `storage` реализует работу с БД. Планировщик только запускает сценарий, не дублирует его логику.

Сейчас CLI позволяет проверить доступ, получить логи и выполнить `analyze --file PATH`. Локальный путь: `input.LokiFileSource → app.AnalysisService → analyzer → cli`. Анализ не загружает `.env` и не создает сетевых клиентов. Команды одного цикла и повторной обработки появятся вместе с БД; REST будет читать подготовленные данные.

## Модели результата

В [model/order.go](../internal/model/order.go) уже определены `OrderEvent`, `OrderState`, `AnalysisResult` и `ResellerSummary`. Остальные модели и дополнительные поля хранения в таблице ниже — требования будущих этапов; пустые структуры заранее не создаются.

| Модель | Минимальные данные |
| --- | --- |
| `CollectionRun` | ID запуска, проект, `[start,end)`, время запуска/окончания, результат `complete/partial/failed`, безопасная причина, число событий/запросов/байт |
| `StoredEvent` | Источник и окружение, идентичность записи, проект, время Loki/приложения/получения, точный исходный текст, все поля JSON, метки и metadata. ID заказа/реселлера, сервер, pod и другие известные поля — отдельно для поиска, если присутствуют |
| `OrderEvent` | Сейчас: проект, время Loki, ID заказа/позиции/реселлера, тип события, исходный статус, уровень, время приложения и признак известной ошибки. Позднее: ссылка на сохраненную запись и версия правил |
| `OrderState` | Сейчас: `(project, order_id)`, реселлер/его конфликт, состояние, исходный статус, первое/последнее время, события и число известных ошибок. Позднее: подтвержденное время завершения и событие-основание |
| `AnalysisResult`, `ResellerSummary` | Число исходных и помеченных демонстрационных записей, заказы, причины пропуска, число известных ошибок; счетчики заказов/состояний/ошибок по проекту и реселлеру, включая `Provisioned` |
| `AggregatedIssue` | Проект, шаблон, количество событий, первое/последнее появление, 1–2 очищенных примера |
| `CollectionCheckpoint` | Проект и граница непрерывно сохраненного периода; позиция анализа и версия правил хранятся отдельно |
| `Anomaly` | Проект, правило, период, измеренное значение, порог, состояние, первое/последнее наблюдение |
| `Notification` | ID аномалии, тип уведомления, целевой чат, состояние доставки, число попыток и время следующей попытки |

`Count` у ошибки — число событий, а не число заказов. Количество уникальных заказов считается отдельно. Сырые записи и очищенные примеры — разные представления: исходный текст не возвращается в интерфейсы автоматически.

## Разбор и связывание событий

- JSON внешнего ответа Loki и JSON строки приложения разбираются независимо; строка другого формата остается допустимой записью Loki.
- ID заказа берется из явного `orderId` либо из `id` только для заранее определенных типов событий заказа. `id` из `create order item` обозначает позицию; родитель берется из `orderId`.
- Отсутствующий ID не заменяется случайным значением. Событие остается несвязанным с причиной и учитывается в диагностике.
- `context=orders` сам по себе не доказывает принадлежность события конкретному заказу.
- Отсутствие ошибки не доказывает успех. `order created` и `status=provision` в имеющемся примере не подтверждают завершение обработки.
- Исходный статус приложения сохраняется отдельно от `unknown`, `in_progress`, `provisioned`, `succeeded`, `failed`. Отмену и повторные попытки нужно описать явными правилами до реализации классификатора.
- Ошибка JSON, неизвестное сообщение и бизнес-ошибка заказа учитываются раздельно. Одна поврежденная строка не прерывает обработку всего окна.
- Для одного набора событий результат должен быть одинаковым независимо от порядка получения и разбиения на страницы.

Основное время сортировки и окон в прототипе — timestamp Loki в UTC. Время приложения в миллисекундах сохраняется отдельно и не подменяет timestamp Loki. При одинаковом времени применяется устойчивый технический порядок для воспроизводимости; он не доказывает бизнес-порядок. Конфликт конечных состояний без согласованного правила дает `unknown` с причиной, а не произвольный успех.

Позднее событие запускает пересчет затронутого заказа по его сохраненной истории. Старое событие не должно просто перезаписать итог более нового события. История и идентичность всегда ограничены проектом: одинаковый ID в двух проектах — разные заказы.

## Правила локального анализатора

Распознаются 14 точных сообщений при `context=orders`; похожие тексты не классифицируются по догадке. Явный `orderId` всегда имеет приоритет. Подстановка `id` разрешена только в отмеченных строках таблицы.

| `msg` | ID заказа | Тип события | Влияние на состояние |
| --- | --- | --- | --- |
| `creating order` | `orderId`, иначе `id` | `creating_order` | `in_progress` |
| `sending order to provision` | `orderId`, иначе `id` | `sending_order_to_provision` | `in_progress` |
| `order created` | `orderId`, иначе `id` | `order_created` | `in_progress` |
| `order received successfully` | `orderId`, иначе `id` | `order_received_successfully` | Ответ на чтение; само по себе `unknown` |
| `getting order` | `orderId`, иначе `id` | `getting_order` | Чтение; само по себе `unknown` |
| `checking order exists` | `orderId`, иначе `id` | `checking_order_exists` | Чтение; само по себе `unknown` |
| `create order item` | Только `orderId`; `id` — позиция | `create_order_item` | `in_progress` |
| `remove order field in item` | Только `orderId`; `id` — позиция | `remove_order_field_in_item` | `in_progress` |
| `order items provisioned` | Только `orderId` | `order_items_provisioned` | Обработаны позиции; само по себе `in_progress` |
| `order provisioned` | Только `orderId` | `order_provisioned` | `provisioned`: этап обработки всего заказа подтвержден |
| `order create error order still being provision` | Только `orderId` | `order_create_error_still_provisioning` | Счетчик ошибок +1, не доказывает `failed` |
| `order create error order not found` | Только `orderId` | `order_create_error_not_found` | Счетчик ошибок +1, не доказывает `failed` |
| `error provisioned, timeout exceeded when trying to connect` | Только `orderId` | `order_provision_error_timeout` | Счетчик ошибок +1, не доказывает `failed` |
| `get artifacts skipped, order not completed or expired` | Только `orderId` | `order_artifacts_skipped` | Пропущено чтение артефактов; само по себе `unknown` |

Если есть `order provisioned`, анализатор выставляет `provisioned` — «Этап обработки подтвержден». Более позднее чтение, промежуточное событие или известная ошибка операции не отменяют этот установленный факт. При отсутствии подтверждения распознанная активность дает `in_progress`; только чтение или ошибки дают `unknown`. `in_progress` означает наблюдавшуюся активность без подтверждения этапа обработки, а не ошибку или доказательство обработки прямо сейчас.

`order received successfully` встречается после `getting order` и до, и после выполнения этапа обработки: это успешный ответ на чтение. Он не запускает обработку и не подтверждает ее завершение. `order items provisioned` подтверждает только позиции и само по себе не заменяет `order provisioned`. Ошибка таймаута подключения не доказывает окончательное падение заказа; последующее подтверждение этапа сохраняется. Пропуск артефактов объединяет две возможные причины («не завершен» или «истек»), поэтому не используется для выбора состояния или признака ошибки.

Известные ошибки остаются в истории и счетчиках независимо от последующего подтверждения; их число не равно числу неуспешных заказов. Последний непустой исходный `status` сохраняется отдельно. `provisioned` пока не означает `succeeded` для всего бизнес-процесса: конечный результат, отмены и повторные попытки требуют отдельных правил. Значения `succeeded`/`failed` предусмотрены моделью, но текущие правила их не выставляют. При подтвержденном новом цикле обработки понадобится модель попыток; сейчас анализатор сообщает факты имеющейся истории без определения нового цикла.

Причины пропуска: `invalid_json` — некорректная строка/типы полей; `unrelated_context` — другой контекст; `unknown_event` — неизвестное сообщение; `missing_order_id` — известное сообщение без допустимого ID заказа. Они считаются раздельно. Ошибка внешнего формата JSON Loki или текстового экспорта Grafana, отсутствие метки `app` или превышение лимита файла останавливают всю команду с понятной диагностикой. TXT требует общих меток и строк вида `UnixMillis<TAB>RFC3339<TAB>сообщение`; временные поля сверяются, проект берется из `Common labels.app`. Оба формата ограничены 10 МиБ и 100 000 записями. Заголовок сводки экспорта не доказывает полноту периода: экспорт может быть ограничен количеством строк.

[orders-analysis.txt](../examples/orders-analysis.txt) — синтетический контрольный пример: 12 записей, 2 заказа, 11 распознанных событий, 1 известная ошибка и 1 неизвестное сообщение. У `demo-order-001` 9 событий, одна ошибка операции и последующее подтверждение этапа обработки (`provisioned`). У `demo-order-002` два события чтения и `unknown`. В сводке реселлера A один заказ с подтвержденным этапом обработки и одно событие ошибки; у реселлера B один заказ с неизвестным исходом. Счетчики относятся только к прочитанному файлу; анализатор не доказывает полноту выгрузки.

`app.AnalysisService` заполняет `AnalysisResult.SyntheticRecords` числом записей из потоков с явной меткой `dataset=synthetic-example`, в том числе пропущенные. CLI отмечает целиком демонстрационный или смешанный набор. Эта метка не проверяет вымышленность содержимого; отсутствие метки также не доказывает, что данные реальные. ID не используются для определения демонстрационного набора.

Консольный отчет использует русские названия событий и причин пропуска. По умолчанию показаны до 10 историй заказов: сначала с известными ошибками, затем остальные без подтверждения этапа, затем остальные; `--all-orders` снимает лимит историй. В каждой истории видны последние пять событий по времени, а последняя известная ошибка дополнительно выводится отдельно, если она старше этого фрагмента. Общие счетчики и отчеты реселлеров вычисляются по всему файлу. ID выводятся из файла; отсутствие сырого сообщения не является гарантией обезличивания.

## Связь с реселлером

История объединяется по `(project, order_id)`. Непустой `resellerId` из распознанного события относится ко всему заказу, даже если в других событиях поле отсутствует. Неизвестные и пропущенные строки не используются для дополнения связи. Имя реселлера сервис логов не угадывает: админка связывает ID со своим справочником.

Один подтвержденный в истории ID дает связь с реселлером. Если ID отсутствует во всей истории, он остается пустым. Два разных непустых ID дают `reseller_conflict=true` и пустой итоговый ID: выбирать последний реселлер по времени небезопасно. Исходные значения остаются в событиях. Сводка выводит такие заказы в отдельной группе без установленного реселлера; CLI различает отсутствие и конфликт в сводке заказов.

`ResellerSummary` считает заказы, их состояния и известные события ошибок отдельно по `(project, reseller_id)`. Счетчик `Provisioned` отражает подтвержденный этап обработки и не входит в число конечных бизнес-успехов. Ошибка события не равна неуспешному заказу. Эти локальные счетчики — основа будущих отчетов через REST; запросы за период, права доступа и хранение появятся на следующих этапах.

## Фильтрация и агрегация ошибок

Нужны два независимых сценария: построение истории заказов и просмотр выбранных сообщений/групп ошибок. Фильтр `ERROR`/`CRITICAL` применяется во втором сценарии. Поля уровня и правила их интерпретации подтверждаются на логах `sds-orders`; числовой `30` не получает название уровня по догадке.

Подстрока и regex могут искать конкретный email, userID или URL в исходных данных до нормализации. Длина шаблона и объем входных записей ограничиваются настройками; регулярное выражение компилируется один раз на операцию. Некорректное выражение возвращает понятную ошибку.

Для группировки заменяются только подтвержденные динамические поля: идентификаторы в известных полях, email, timestamps. Нельзя заменять все числа подряд: HTTP-статус, код ошибки, сумма или длительность могут отличать разные причины. Маскирование длительности вводится отдельным правилом, если такие события действительно нужно объединять.

Минимальный результат соответствует исходному плану:

```go
type AggregatedIssue struct {
    Template     string
    Count        int
    LiveExamples []string
}
```

`LiveExamples` содержит не более двух разных очищенных примеров. Шаблон и примеры проходят удаление секретов и ненужных персональных данных перед сохранением в публичное представление. Нормализация шаблона не заменяет очистку примеров.

Ключ группы включает проект и шаблон; версия правил хранится с результатом. При смене правил агрегаты пересчитываются из событий, а не прибавляются поверх старого результата. Повторяющиеся реальные ошибки увеличивают `Count`, даже если текст одинаковый.

## Снимок каждые две минуты

Снимок — ограниченный пакет событий за период `[start,end)` и запись о результате его получения. Он не означает повторную выгрузку всей истории проекта.

1. Прочитать сохраненную позицию проекта. При первом запуске загрузить доступные последние сутки небольшими окнами; начальный период задается конфигурацией.
2. Один раз зафиксировать конец окна как текущее время минус задержка поступления логов. Начало взять от позиции с небольшим перекрытием уже обработанной истории.
3. Получить данные через `FetchLogs`, соблюдая пределы периода, записей, запросов, байт и времени. Большой период догонять последовательными ограниченными окнами.
4. Проверить `Complete`. При неполноте сохранить статус и причину; позицию успешной обработки не продвигать через это окно.
5. Для полного окна в одной транзакции сохранить исходные события и продвинуть позицию сбора. Неизвестный формат сообщения приложения не мешает сохранению его исходной строки. При сбое записи позиция не продвигается.
6. Отдельно прочитать сохраненные события, выполнить анализ и зафиксировать результаты вместе с позицией анализа. При ошибке повторить анализ с этой позиции; сбор новых логов продолжается. После подключения аномалий их изменения и задания уведомлений сохраняются вместе с результатом анализа.
7. После фиксации результатов отправлять задания уведомлений отдельным исполнителем. После рестарта он продолжает очередь из БД. Ошибка Telegram не откатывает сбор.

Для MVP неполный пакет не публикуется как завершенная обработка: сохраняются сведения о попытке, затем окно повторяется или делится. Нельзя признать окно пустым после ошибки HTTP, обрезанного ответа или достижения лимита. Если даже минимальный интервал насыщен, требуется видимый статус неполноты и ручное решение; пропуск событий недопустим.

Интервал задается настройкой: по умолчанию `2m`, при необходимости `5m`. Циклы одного проекта не выполняются параллельно. Если работа длится дольше выбранного интервала, второй цикл не накапливается в неограниченной очереди: следующий продолжает сохраненную позицию, а отставание отображается явно. Контекст отменяет запросы и ожидание при завершении процесса.

`Complete` означает полноту ответа на момент чтения Loki, а не окончательность истории. Перекрытие позволяет найти часть запоздавших записей; события старше выбранного перекрытия обнаруживаются только явной повторной обработкой периода. Длина перекрытия и задержка конца окна задаются по наблюдаемой задержке доставки и описываются в конфигурации.

## Повторная загрузка и идентичные события

Защита от повторной загрузки и агрегация ошибок решают разные задачи. Первая предотвращает двойной учет одного события при повторе окна. Вторая объединяет разные события по похожему тексту, сохраняя их количество.

Предпочтителен устойчивый ID события из источника, если его наличие и уникальность подтверждены. Номер заказа таким ID не является: у заказа много событий. Пока исходный ID не подтвержден, требуется стратегия сохранения кратности одинаковых записей.

Для прототипа без ID: идентичность группы определяется проектом, timestamp Loki, канонически упорядоченными метками/metadata и точным текстом. В полном ответе сохраняется количество одинаковых записей, а при перекрытии сравнивается уже известная кратность и добавляется только разница. Уменьшение наблюдаемого количества не удаляет ранее сохраненные события автоматически. Полный набор меток нужен, чтобы одинаковые строки из разных потоков не склеились.

Один уникальный хеш от timestamp и текста без учета кратности неприемлем. При отсутствии ID две полностью неразличимые записи невозможно надежно различить как отдельные сущности; это ограничение должно быть описано и проверено тестами. Изменение кратности проверяется только по полным окнам, содержащим соответствующий timestamp целиком.

## Хранение и повторная обработка

Выбрана PostgreSQL; Kafka не используется. Подключение, драйвер и миграции предстоит реализовать. Начальная схема: `log_events` — исходные события, `orders` — сводки заказов, `collection_runs` — покрытие и ошибки сбора, `checkpoints` — позиции сбора и анализа. Таблицы агрегатов и уведомлений добавляются вместе с их сценариями.

Требуется сохранять полный контекст каждого события: точный исходный текст отдельно от разобранного JSON, все поля корректного JSON в `jsonb`, все метки потока и metadata, источник, окружение и времена. Часто используемые поля выносятся в колонки для поиска, но неизвестные поля не отбрасываются. Сервер, pod, namespace и container сохраняются у событий, если присутствуют; у одного заказа могут встречаться несколько значений. Пропущенные анализатором сообщения тоже остаются в хранилище и доступны для будущего пересчета; для невалидного JSON сохраняется исходная строка без разобранного объекта.

Сейчас `LogRecord` содержит исходную строку и контекст Loki в памяти, а `OrderEvent` — только выбранные поля. Сохранение полной истории в БД и связь результатов анализа с исходными событиями пока не реализованы.

Сутки — период отчета, а не граница истории заказа. Для ошибки «заказ не найден» анализ должен искать более ранние события создания, их результаты и последующие чтения в сохраненной истории, сопоставляя реселлера и экземпляры приложения. Сам запрос неизвестного заказа не доказывает, что он раньше был успешно создан; отсутствие предыстории обозначается явно.

Срок хранения событий, очищенных примеров и агрегатов задается отдельно. Повторный пересчет возможен только за период, для которого сохранились необходимые события; попытка пересчета за удаленную историю возвращает явное ограничение. Исходные сообщения, включая неизвестные, хранятся без изменения в пределах настроенного срока с ограниченным доступом. Для REST и Telegram создаются отдельные очищенные представления; очистка не заменяет исходную историю.

Миграции, ограничения уникальности и индексы входят в прототип. Исходные события и позиция сбора должны быть согласованы после сбоя; результаты и позиция анализа фиксируются своей транзакцией. Границы транзакций определяются сценарием приложения, а не HTTP-обработчиком. Доступы к БД и права на локальные файлы ограничиваются нуждами сервиса.

При ручной повторной обработке счетчики пересчитываются, а не суммируются повторно. По умолчанию такая операция не рассылает исторические Telegram-уведомления. Версия правил и обработанный период сохраняются для диагностики.

## Пульс и правила аномалий

Пульс показывает количество заказов с подтвержденным итогом за временную корзину. В прототипе один заказ учитывается один раз по текущему подтвержденному исходу и времени соответствующего конечного события. Несколько сообщений об одной ошибке не превращаются в несколько неуспешных заказов.

Доля ошибок: `failed / (succeeded + failed)`. При нулевом знаменателе значение отсутствует (`null`), а не равно нулю. `unknown`, `in_progress` и `provisioned` не попадают в знаменатель; их количество выводится отдельно как состояние на момент обновления. Это график исходов заказов, а не доля ошибок среди отдельных строк логов.

При исправлении исхода поздним событием или повторной обработкой старые и новые корзины пересчитываются. Если поведение повторных попыток не согласовано, противоречивый результат не включается в подтвержденные исходы. Точное правило выбора конечного события входит в этап 1.

Первый набор правил: доля неуспешных заказов выше порога при достаточной выборке; число неуспешных заказов выше порога; подтвержденный незавершенный заказ обрабатывается дольше допустимого времени. Значения порогов и длительность периода задаются настройками после изучения нормального потока.

При неполном сборе или большом отставании бизнес-показатели помечаются неполными и не используются как доказательство восстановления. Отдельно показывается техническая проблема сбора. Пустое окно и отсутствие входящих заказов сами по себе не доказывают падение сервиса.

Аномалия имеет состояния открыта/восстановлена. Для пары «проект, правило» допускается одна активная аномалия: повторное наблюдение обновляет ее. Новое нарушение после восстановления создает отдельный эпизод с новым ID. Изменение аномалии и постановка уведомления фиксируются атомарно, поэтому сбой между сбором и отправкой не теряет задание. Очередь уведомлений хранится в БД; подавление повторов работает и после перезапуска. Ошибка отправки видна отдельно от бизнес-аномалии.

## Проверки приемки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Только имеющийся пример создания заказа | Нет выдуманного конечного успеха |
| Ошибка операции, затем `order provisioned`, затем чтение | Этап обработки подтвержден; ошибка остается в истории |
| Только `getting order` и `order received successfully` | Исход неизвестен; чтение не считается обработкой |
| Только `order items provisioned` | Есть активность, подтверждение всего заказа отсутствует |
| Таймаут подключения и более позднее подтверждение | Ошибка сохранена, этап обработки подтвержден |
| Только пропуск выдачи артефактов | Причина показана; конечный исход не придуман |
| Текстовый экспорт Grafana с согласованными датами | Получены записи с проектом из общих меток |
| Разные даты в двух временных полях TXT | Ошибка формата с номером строки, без частичного результата |
| Больше 10 заказов в файле | Сводка учитывает все заказы; ограничен только подробный показ |
| Позиция с `id` и родительским `orderId` | Позиция связана с заказом, не создает отдельный заказ |
| Неизвестные JSON-поля, метки, metadata и несколько pod у заказа | Полный контекст остается у исходных событий и доступен для пересчета |
| Сбой анализатора после записи исходных событий | Сбор продолжается, анализ повторяется с собственной позиции |
| Повтор полного окна после рестарта | Счетчики и количество событий не меняются |
| Две полностью одинаковые строки в одном ответе | Сохраняется кратность два, повтор окна не дает четыре |
| Несколько страниц и совпадающие timestamps | Нет потерь на границах, либо явно отмечена неполнота |
| Частичная выгрузка или ошибка записи | Позиция не перескакивает через необработанные данные |
| Запоздавшее конечное событие | Заказ и соответствующие корзины пересчитаны |
| Неизвестная или поврежденная строка | Диагностика увеличилась, обработка остальных событий продолжается |
| Ошибки HTTP 400 и 500 с похожим текстом | Не склеены одним общим маскированием всех чисел |
| Нет заказов или нет данных | Не показывается подтвержденная доля ошибок 0% |
| Повторное срабатывание того же правила | Одно открытие аномалии, без нового задания на каждое чтение |
| Недоступен Telegram | Сбор и запись продолжаются; доставка повторяется ограниченно |

Тесты анализа используют локальные примеры и не требуют токенов. Транзакции и повторный запуск будут проверяться на PostgreSQL. Только после этих проверок выполняется ограниченный прогон на реальных данных.
