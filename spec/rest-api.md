# План REST API для админки

REST предоставляет сохраненные результаты обработки: заказы, историю событий, группы ошибок, пульс и аномалии. Все ручки ниже планируются; HTTP-сервера в проекте пока нет. Основной порядок работ находится в [чек-листе](README.md), смысл данных — в [правилах обработки](processing.md).

## Область первого API

Первый API работает только на чтение. Запрос страницы админки не вызывает Loki, не запускает анализ и не отправляет сообщения. Сбор, ручная повторная обработка и миграции выполняются отдельными командами/процессами. Произвольный LogQL и вывод сырых логов через REST в MVP не включаются.

Используется `net/http`. HTTP-адаптер разбирает параметры, проверяет доступ, вызывает сценарий приложения и преобразует результат в JSON. SQL и правила заказов остаются в своих слоях. Служебный токен Grafana не дает доступ к этому API и не передается в него.

```text
cmd/lokid/main.go
  → создает конфигурацию, PostgreSQL, сервисы чтения и HTTP-сервер
  → internal/rest: маршруты, параметры, DTO, ошибки
  → internal/app: сценарии чтения
  → internal/storage: запросы к PostgreSQL
```

Новый entrypoint `cmd/lokid` создается при реализации; `cmd/lokictl` сохраняет диагностические команды. Сервер и сборщик могут работать в одной реплике, но имеют отдельные обязанности и общий управляемый контекст завершения. Точка входа явно передает хранилище сервису и сервис HTTP-обработчику, как сейчас соединяются компоненты CLI. Отдельный слой сборки зависимостей не требуется.

## Ручки

| Метод и путь | Назначение | Основные параметры |
| --- | --- | --- |
| `GET /healthz` | Процесс отвечает | Нет |
| `GET /readyz` | БД доступна и миграции применены | Нет |
| `GET /api/v1/projects` | Проекты, настроенные для сбора | Нет |
| `GET /api/v1/collector/status` | Последний запуск, позиция, отставание и неполнота | `project` |
| `GET /api/v1/orders` | Список состояний заказов | `project`, `reseller_id`, `start`, `end`, `state`, `order_id`, `limit`, `cursor` |
| `GET /api/v1/orders/{order_id}` | Текущее состояние одного заказа | `project` |
| `GET /api/v1/orders/{order_id}/events` | История заказа с очищенным содержимым | `project`, `start`, `end`, `limit`, `cursor` |
| `GET /api/v1/issues` | Шаблоны ошибок, количество, 1–2 очищенных примера | `project`, `reseller_id`, `start`, `end`, `limit`, `cursor` |
| `GET /api/v1/pulse` | Корзины для графика исходов заказов | `project`, `reseller_id`, `start`, `end`, `step` |
| `GET /api/v1/resellers/summary` | Заказы, состояния и события ошибок по реселлерам | `project`, `reseller_id`, `start`, `end`, `limit`, `cursor` |
| `GET /api/v1/anomalies` | Аномалии и причина срабатывания | `project`, `start`, `end`, `state`, `limit`, `cursor` |

`/readyz` не делает внешний запрос к Loki или Telegram при каждом вызове. Их недоступность отражается в статусе сбора/доставки; готовый к чтению сервер продолжает отдавать сохраненные данные. Проверка доступности БД ограничена таймаутом. `/healthz` и `/readyz` возвращают только минимальный статус без адресов, токенов и внутренних ошибок.

## Параметры и порядок записей

`project` обязателен для предметных ручек и проверяется по разрешенным проектам; в первом прототипе это `sds-orders`. Одинаковые ID заказов в разных проектах не смешиваются.

`reseller_id` ограничивает результат заказами с установленной связью с данным реселлером. Отсутствующая или конфликтующая связь не совпадает ни с одним конкретным ID. При отсутствии фильтра пользователь получает только разрешенную ему область данных; отсутствие фильтра не расширяет права. Карточка и события проверяют доступ через реселлера заказа, даже если параметр не передан. Имена реселлеров берет админка из своего справочника по ID.

Сводка реселлеров агрегирует заказы, чье последнее событие входит в период, по их текущему состоянию; количество событий ошибок считается по времени самих ошибок в этом периоде. В ответе нужны отдельные названия счетчиков и описание периода для каждого. Подтвержденный этап обработки (`provisioned`) имеет отдельный счетчик. Пульс учитывает только подтвержденные конечные исходы `succeeded`/`failed`; этот этап в их число не включается. Аномалии проекта нельзя автоматически приписывать реселлеру: фильтр для них появится после правил аномалий по реселлерам.

`start` и `end` задаются вместе в RFC3339 с часовым поясом. Интервал `[start,end)`; в ответе время всегда UTC. Если обе границы отсутствуют, используется последний час. Начальный предел периода — 24 часа, `limit` по умолчанию 50, максимум 200. Это планируемые ограничения API, отдельные от лимитов клиента Loki.

| Выборка | Как применяется период | Порядок |
| --- | --- | --- |
| Заказы | По последнему событию заказа в Loki | `last_event_at DESC`, затем `order_id ASC` |
| События заказа | По времени события Loki | `timestamp ASC`, затем устойчивый ID записи |
| Группы ошибок | Счетчик и примеры вычислены по событиям указанного периода | `count DESC`, затем устойчивый ID группы |
| Аномалии | Аномалии, активные хотя бы часть запрошенного периода | `opened_at DESC`, затем ID |
| Пульс | По времени подтвержденного конечного события | Начало корзины по возрастанию |

Список заказов показывает их текущее состояние; фильтр времени не означает восстановление состояния «как оно выглядело тогда». `state` для заказов принимает `unknown`, `in_progress`, `provisioned`, `succeeded`, `failed`; для аномалий — `open` или `resolved`. `provisioned` обозначает подтвержденный этап обработки по `order provisioned`; это отдельный этап, не конечный бизнес-успех. Успешное чтение `order received successfully` состояние не изменяет. Семантика конечных исходов, отмены и повторных попыток уточняется до расширения классификатора.

Пагинация использует непрозрачный cursor с ключами сортировки и привязкой к фильтрам. Поврежденный cursor, изменение его фильтров и недопустимые параметры дают `400`. API не обещает неизменную историческую выборку между страницами: при новых/поздних событиях результат может обновиться. Клиент использует устойчивые ID, а при смене фильтров начинает выборку заново.

Для пульса `step` выбирается из `2m`, `10m`, `1h`; по умолчанию `2m`, максимум 720 корзин. Корзины привязаны к UTC, крайние ограничены запрошенным периодом. При превышении предела требуется укрупнить шаг; сервер не обрезает результат молча.

## Формат ответа

Коллекции используют `items` и `meta`, карточка — `item` и `meta`. Поля JSON записываются в `snake_case`; ID заказов и записей передаются строками. Время — RFC3339Nano в UTC, а не большое число наносекунд, теряющее точность в JavaScript.

Пример запланированного ответа списка заказов:

```json
{
  "items": [
    {
      "project": "sds-orders",
      "order_id": "example-order",
      "reseller_id": "example-reseller",
      "reseller_conflict": false,
      "state": "in_progress",
      "source_status": "provision",
      "last_event_at": "2026-10-09T18:10:45.393295815Z"
    }
  ],
  "meta": {
    "generated_at": "2026-10-09T18:14:00Z",
    "data_updated_at": "2026-10-09T18:13:50Z",
    "collected_through": "2026-10-09T18:12:00Z",
    "complete": false,
    "reason": "collection_lag",
    "next_cursor": null
  }
}
```

`generated_at` — время ответа, `data_updated_at` — время фиксации результатов обработки, `collected_through` — граница непрерывно обработанного периода проекта. До первого успешного сбора последние два значения могут быть `null`.

`complete` показывает покрытие запрошенных данных сбором и обработкой с учетом доступного срока хранения. Оно не гарантирует, что в Loki больше не появятся запоздавшие события или что история заказа началась после начала наблюдения. `next_cursor` отвечает отдельно за наличие следующей страницы; пагинация не делает `complete=false`.

Пустая успешная выборка возвращает `200`, `items: []`. При неполном сборе сохраненная часть также может быть возвращена с `200`, но обязательно с `complete: false` и безопасным кодом причины. Нельзя заменять ошибку БД пустым массивом. У пульса дополнительно нужен признак полноты каждой корзины, чтобы админка показывала пробелы на графике.

Карточка заказа включает `reseller_id` (или `null`), `reseller_conflict`, состояние, исходный статус, время событий и ссылку на событие-основание. Полная история читается отдельной ручкой с пагинацией. В группах ошибок счетчик, первое/последнее появление и примеры относятся именно к запрошенному периоду. Пульс возвращает `succeeded`, `failed`, `failure_rate` и полноту корзины; счетчики `unknown`/`in_progress`/`provisioned` выводятся отдельно с моментом актуальности.

## Ошибки и доступ

```json
{
  "error": {
    "code": "invalid_period",
    "message": "Период должен быть положительным и не более 24 часов"
  }
}
```

| HTTP | Смысл |
| --- | --- |
| `400` | Некорректные параметры, фильтры или cursor |
| `401` | Отсутствует или неверен токен API |
| `403` | Нет доступа к запрошенному проекту или реселлеру |
| `404` | Заказ или маршрут не найден |
| `405` | Метод не поддерживается |
| `500` | Непредвиденная внутренняя ошибка |
| `503` | Не готова или временно недоступна БД |

Внешняя ошибка не включает SQL, тело лога, строку подключения или ошибки транспорта с URL. Данные для диагностики записываются отдельно с безопасным контекстом. Секреты и исходный текст логов в access log не попадают.

Планируемые настройки: `HTTP_ADDR=127.0.0.1:8080` и отдельный `API_TOKEN` без значения по умолчанию. Предметные ручки требуют `Authorization: Bearer <API_TOKEN>`; сравнение токена выполняется без утечки через время сравнения. Эти настройки добавляются в загрузчик и `.env.example` одновременно с сервером: текущий загрузчик неизвестные ключи не принимает.

Для первого прототипа одна служебная учетная запись API имеет доступ к явно настроенным проектам. Бэкенд админки использует этот токен, а браузер — существующую авторизацию админки. Бэкенд админки обязан проверить права пользователя на запрашиваемого реселлера до служебного вызова: `reseller_id` — фильтр, а не разрешение доступа. Для нескольких ограниченных служебных клиентов API потребуется явная область разрешенных реселлеров в их учетных данных. Заказы без установленного реселлера доступны только операторам с отдельным правом на общую диагностику. Токен не встраивается в JavaScript. Доступ вне localhost организуется через HTTPS и существующий защищенный вход инфраструктуры. CORS по умолчанию выключен; разрешенный origin добавляется только при конкретной схеме интеграции.

- [ ] Добавить `cmd/lokid`, типизированную конфигурацию сервера и соединение компонентов непосредственно в `main.go`.
- [ ] Описать DTO и контракт `spec/openapi.yaml`, включая отсутствующие значения, статусы и ограничения.
- [ ] Добавить сервисы чтения в `app` и запросы к БД с параметрами; не копировать туда логику CLI-печати.
- [ ] Реализовать маршруты и общую проверку периода, проекта, `reseller_id`, состояния, лимита и cursor.
- [ ] Добавить отчеты по реселлерам, отдельно определить отсутствующую/конфликтующую связь и источник названия в админке.
- [ ] Добавить отдельную авторизацию API, очистку ответов и единый формат ошибок.
- [ ] Проверить запрет чтения чужого реселлера через список, ID заказа, историю, сводку, группы ошибок и пульс; отсутствие фильтра не должно обходить права.
- [ ] Задать таймауты чтения заголовков, записи и простоя, ограничение заголовков и контекст запросов к БД.
- [ ] Реализовать корректное завершение HTTP-сервера с ограниченным временем ожидания активных запросов.
- [ ] Проверить `healthz`/`readyz`, авторизацию, все ручки, пустые данные, ошибки БД и неполные периоды через `httptest`.
- [ ] Проверить пагинацию без пропусков/дублей на неизменном наборе и документированное поведение при обновлении данных.
- [ ] Проверить, что чтение REST не вызывает Loki/Telegram и не возвращает сырые секреты из примеров.
- [ ] Добавить примеры `curl` с локальными переменными для токена и описание подключения админки.

Готовность этапа: админка получает согласованные результаты из БД; ответы ограничены по объему, защищены отдельным доступом и показывают свежесть и неполноту. Ручки управления сбором, изменения настроек, WebSocket и публичный доступ без инфраструктурной авторизации остаются вне первого API.
