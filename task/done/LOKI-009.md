# LOKI-009 Распознавать события заказа и строить историю обработки

> Карточка фиксирует результат раннего этапа. Возможности первой версии Telegram описаны в [текущей приемке](../prototype.md).

- **Тип:** Задача
- **Статус:** Выполнено
- **Приоритет:** Средний
- **Компонент:** Анализатор
- **Этап:** Выполнено
- **Зависимости:** [LOKI-007](LOKI-007.md), [LOKI-008](LOKI-008.md)

## Цель

Собирать из известных сообщений историю заказа, отделяя наблюдаемую обработку, чтение и ошибки операций.

## Что сделано

- [x] Анализатор распознает 14 типов сообщений контекста `orders`.
- [x] Явный `orderId` имеет приоритет; `id` используется как ID заказа только для известных типов сообщений.
- [x] Позиции связываются с родительским заказом; группировка учитывает проект.
- [x] Истории сортируются; повторные записи сохраняются. При одинаковом времени применяется стабильный технический порядок.
- [x] Неизвестные события, посторонний контекст, поврежденный JSON и отсутствие ID учитываются по причинам пропуска.
- [x] `order provisioned` устанавливает `provisioned`, который сохраняется после чтения и ошибок; сообщения об ошибках остаются в истории.

## Критерии приемки

- [x] Успешное чтение не считается подтверждением обработки, а `order items provisioned` — подтверждением всего заказа.
- [x] Ошибка операции не превращается автоматически в окончательное падение заказа.
- [x] Порядок входных записей не меняет сводку; конечные `succeeded` и `failed` не выдумываются.

## Границы задачи

Анализируется одна загруженная выборка без памяти предыдущих запусков. `OrderEvent` содержит выбранные поля, а пропущенные строки представлены счетчиками; полного архива событий этот результат не заменяет.
